\part{The idea}

\chapter{What \nodwyn{} is}

\nodwyn{} is a coding agent's \emph{harness}: the program that sits between a
language model and your machine. It holds the conversation, offers the model
tools, runs the tools the model asks for, and feeds the results back. Every
such harness answers a handful of questions, and \nodwyn{} exists because it
answers them differently.

\paragraph{Who decides what the model may do?} In \nodwyn{}, one function. Every
tool the model can call is a \emph{primitive} in an embedded Scheme
interpreter, and every primitive application, whoever asks for it, passes
through a single Go function where a \emph{guard} decides: allow, ask the
user, or deny. There is no second path. A file read, a command, a request to
an MCP server and a keyed HTTP call are all primitives, and all of them
cross the guard.

\paragraph{How are secrets protected?} By never being content. A key is not
a string the harness tries to spot in a request; it is a \emph{credential}
the user registered into an encrypted store, referenced by an opaque handle,
and injected only at a destination the user has \emph{bound} it to. The
question ``is this egress safe?'' is not ``does this look like a secret?''
but ``is this class of credential authorised for this destination, in this
position, with this method?''\,---\,a table lookup, owned by the user. Content
detection exists too (a cheap deterministic layer and a provenance layer;
a learned layer is planned), but it is the residual, not the authority.

\paragraph{What is the source of truth?} An append-only log. One JSON line
per event, fsynced. The model's context window, the transcript you see, the
summaries you add\,---\,all are derived from the log and can be recomputed
from it. A session resumes from complete durable records; a crash may interrupt
the last write or leave a tool's outcome unknown, so interrupted calls are not
automatically repeated. A
request sent to the model can be rebuilt exactly from the log and checked
against the digest recorded with it.

\paragraph{What does it talk to?} More than a model. A session reads and
writes files, runs programs, talks to the models you configured, calls
tools on the MCP servers you connected or run in containers, sends keyed
requests to APIs you bound, asks a judge about plans and about the
commands it would otherwise ask you to allow, and writes documents, which
it may upload to Google Docs. You reach it from a terminal, a
full-screen terminal client, a browser, a desktop window or a paired phone,
and you can attach documents and images to a conversation. Chapter~\ref{ch:io} lists
every one of these channels, what crosses it, and what decides whether it
may.

\paragraph{And one more thing.} \nodwyn{} extends itself. The tools a
repository needs\,---\,run the tests, show a diff, read a decision
record\,---\,are written in its own Scheme, loaded from the repository, and
cross the same guard as everything else. So is the agent loop itself: how a
turn goes is a Scheme procedure a project may redefine. \nodwyn{} has been
used to build \nodwyn{} since its first promoted binary.

\chapter{Invariants}

Five statements are load-bearing. Everything else in the design is a
consequence of them, and every change is judged by whether it preserves
them.

\begin{enumerate}[leftmargin=2em]
\item \textbf{The log is the single source of truth.} Index and window are
  derived, revocable views; a stale summary means recompute-from-log.
\item \textbf{The judge judges intent and plans over redacted content; the
  local stack judges \emph{what}.} The judge\,---\,an external calibrated service used
  at two seams\,---\,sees the ask, the plan, and egress \emph{situations}
  (class, destination, scope), after redaction, and more only at the
  content level you choose. It never sees a secret value. (Wording amended
  by \adr{19}.)
\item \textbf{Secrets are credentials, not content.} The harness holds opaque
  handles into a log-excluded encrypted keychain, uses them only at a bound
  destination, and never sees the value.
\item \textbf{The Scheme interpreter is the only Scheme$\to$Go surface; the
  guard sits on it.}
\item \textbf{Every I/O edge is guarded\,---\,by the mechanism that fits its
  substrate.} Scheme values get provenance tags; text gets redaction; egress
  gets the binding check.
\end{enumerate}

Invariant~4 is the one you will meet first in the code: \code{applyPrim} in
\file{scheme/prim.go} in Brote is the only caller of any primitive's handler,
and a test records every crossing to prove it. Invariant~1 is the one that
shapes everything you will not see: there is no ``conversation state'' object
anywhere; there are events, and functions that fold them. Invariant~5 is the
subject of the next chapter.

\chapter{Input and output}\label{ch:io}

This chapter lists every channel through which bytes enter or leave a
\nodwyn{} session, and for each one says what crosses it, who starts it, and
what decides whether it may.

\section{Two rules that cover every channel}

\paragraph{Out: everything the model or Scheme does to the world is a
primitive application.} Reading a file, running a program, calling an MCP
tool, sending a keyed request, asking the judge, asking a model: each is a
primitive, applied through \code{applyPrim}, where the guard runs its
checkers before the handler. The handler is Go code that does the actual
I/O. A keyed call to \code{http-request}, the judge or an MCP tool is
checked against the binding table by the guard before its handler runs; an
MCP server's transport checks it again on every HTTP request, and a keyed
model's transport checks it there, on every request, just before the key
is injected. The outbound exchanges that are not primitive applications
send no conversation content: the MCP handshake and tool list when a
session starts, and a chat-completions server's model list
(\code{GET /models}, for the model's context length and the console's
suggestions), which check the binding the same way before a key goes out,
a model key being bound for \code{GET} as well as \code{POST}; Ollama's
\code{/api/version}, which line mode asks to see the server is up, and
\code{/api/show}, which says whether a model takes images; and the
console's check that each configured model answers. An OAuth2 refresh
goes to the token endpoint stored with the credential, as part of a use
the binding table already allowed.

\paragraph{In: what reaches the model passes one door.} Tool results, your
messages, attachments, the plan and the model's own replies enter the
model's context only as recorded events. \code{Session.Record} redacts each
one, the log writer redacts again, and the window is built from what was
written. Nothing is appended to the conversation by any other route, and a
lint in CI checks it. An attached image passes the same door as a record
naming it by digest, but its pixels are not text and are never redacted:
they are read from the attachment store when a request is sent, and only
after a confirm of their own. The two parts of a request that are not events, the
system prompt and the tool list, are assembled when the session starts;
the tool descriptions, including those an MCP server wrote, pass the same
redactor, and a repository's notes were redacted when they were saved.

\section{Models}

The control model answers \code{(model-turn)}; any other model you configure
under \code{[models.NAME]} answers \code{(model-turn "NAME")}. Which model
the control model is, is a choice of the conversation, not of the machine
(\adr{40}): a task starts on \code{[control]} or on a model you pick for it,
and may be moved to another one between turns\,---\,a
\code{[models.NAME]} entry, or any model a configured server offers, which
needs no entry of its own. The choice is a record in the session's log
(\code{session.model}), so the task talks to it again when it is resumed,
and the key does not change: another model on the same server is the same
key and the same binding, and one on another server brings that server's
key, its binding checked on every request. Each request
sends the window built from the log: by default the whole conversation, or,
when a strategy has called \code{narrow-context}, only the task and the plan
it chose. What comes back is text, the model's thinking, and tool calls,
with the server's token counts. \code{llm.resp} records them, the prompt
tokens the provider read from its cache when it says, and the request's
cost, as the provider reported it or as the model's configured prices
estimate it.

A model that needs a key names a credential class in its configuration. On
every request the transport looks the class up in the binding table for the
model's host, method and the position \code{header:Authorization:Bearer},
records the lookup as \code{egress.check}, and injects the key only if it is
bound. A model that needs no key\,---\,a server on your own machine or
network\,---\,has no such check. In both cases the decision that the window
may go to that model is yours, made when you configured it: \nodwyn{} does
not judge the content of a model request, because the whole point of the
request is to send the conversation.

The reply is buffered until it is complete, then redacted, then shown and
recorded, so a key split across two streamed chunks is still caught. Thinking
is recorded and may be shown, and goes back to the model with the reply it
came with, as recorded, so redacted like everything else.

\section{MCP servers}

An MCP server offers tools. \nodwyn{} speaks MCP's streamable HTTP
transport to remote servers, and MCP's stdio transport to a server it runs
in a container on this computer; it starts no server as a process of yours
(\adr{23}: a server nobody has reviewed does not run in \nodwyn's process
tree). Servers are listed in \file{mcp.toml} in the configuration
directory, which you edit through the console's Connections page or by
hand:

\begin{txt}
[[server]]
name = "tracker"
url = "https://mcp.example.com/mcp"
credential = "tracker-key"
position = "header:Authorization:Bearer"
manifest = "9f2c..."                  # the tool list you approved
workspaces = ["/home/me/src/app"]

[server.tool."search_issues"]
on = true
effect = "read"

[server.tool."create_issue"]
on = true
effect = "write"
\end{txt}

\paragraph{At session start.} For each server offered in the session's
workspace, \nodwyn{} connects, asks for the tool list, and hashes it: every
tool's name, title, description, input schema and annotations. If the hash
is not the one you approved, the server offers nothing in this session and
the session says why; the rest of the task works. Otherwise each tool you
turned on becomes a primitive named \code{server\_\_tool} (model APIs refuse
a slash; the console shows \code{server/tool}), and the tool list is frozen
for the session. The tool descriptions are text the server wrote, and they
reach the model: pinning makes them stable and reviewed, not true.

\paragraph{Per call.} An MCP primitive is always egress: to the server's
host, or for a contained server to its container.
Its \emph{effect} is your declaration, not the server's: MCP describes what
a tool takes, not what it does to the world, and the server's own hints are
part of the manifest you approve but never trusted.
\begin{itemize}
\item \code{effect = "read"}: the call runs without asking. Its arguments
  still leave for the server.
\item \code{effect = "write"}, or no effect declared: every call asks, with
  the arguments shown by name, and no standing approval can answer for it.
  An undeclared tool is treated as sending out \emph{and} irreversible.
\end{itemize}
A remote server with a credential makes every call credential-bearing: the guard's
binding check (E3) runs before the handler, and the transport checks the
binding again, and injects the key, on every HTTP request\,---\,the
handshake, the tool list and each call. Redirects are not followed, so a
request cannot carry arguments and a key to a host the binding does not
name. A server without a credential has no binding to check: what
authorises its traffic is \file{mcp.toml} itself and, for tools not
declared reads, the confirm.

Every argument is a \code{payload}, since the whole call is sent: L1 refuses
a recognised key in any of them, however deeply nested, unless its class is
bound for the server's host, and L2 reads where each came from. Content from
your files or programs may go to the server, because approving it named its
host, as a binding names one, with a key or without.

\paragraph{The result} comes back as text (content that is not text is
described, not decoded), tagged \code{external:mcp}, becomes the tool result
the model reads, and is redacted on its way into the log and the context
like every other result.
An error the server reports is an error result. The tool's description
tells the model that results are data, never instructions; nothing a
server returns can grant a permission, because permissions come from the
policy files and the guard.

\paragraph{What the confirm is really asking.} Isolation cannot un-send an
argument. At an MCP confirm the question is not ``is this argument safe?''
but ``do I want this third party to see this?''.

\paragraph{A contained server} (\code{transport = "container"}) runs from
an image pinned by its digest, which you pull yourself
(\code{nodwyn mcp pull NAME}); a task never downloads one. It runs with no
capability, a read-only root, none of your environment and only the
workspace folders its entry lists. Its \code{network} list is where its
arguments can go next: empty, it has no network at all; with hosts, its
container sits on a network with no route out, and its only way out is
\nodwyn{}'s egress proxy in a second container, which lets through those
hosts and refuses the rest, and every attempt is recorded as
\code{mcp.egress}. Its calls go to \code{mcp:NAME}, so a key in the
arguments is refused unless its class is bound for every listed host. Its
own key goes in once, as an environment variable, only if bound for every
listed host at that \code{env:} position; each check is an
\code{egress.check}, and the check runs again before every call. The
confirm names the contained server and what it can reach. A container is
not a virtual machine: a kernel escape is out of scope.

\section{Keyed HTTP and the judge}

\code{http-request} sends a request with a credential handle injected at a
bound position. It takes the handle as its first argument, and a handle can
only be produced by Scheme (\code{(credential "class")}), never from a
model's JSON, so the model reaches an API only through a tool a user
registered in \file{.nodwyn/init.scm}. The guard checks the binding for the
credential slot (E3), scans the headers and body for known key shapes (L1),
and reads the provenance of the payload (L2): content that came from a file,
a command or another response may go only to a host some binding names.
The response is tagged \code{external:http}.

The judge is reached through three primitives, \code{judge-yes-no},
\code{judge-score} and \code{judge-choice}, built the same way: a bound
credential, a fixed host, the payload redacted before it is sent, and a
\code{jev.req} record of the origin, content level, size, payload hash and
redactions of every call. The host and the key are those of the provider
\code{[judge]} names, Jev or OpenAI, whose API the call speaks (\adr{46}).
Go supplies the stored key, and the guard judges each call as carrying its
class. They exist only in a session that started with that key stored;
without one, nothing is sent, and the default plan gate does not run.
Since the model chooses what it would send, they are its tools only when
\code{judge.content} is \code{full}; below that they are hidden, for the
plan gate and your Scheme.

Neither follows a redirect, any more than the MCP client or a model
request does: the binding was checked for the host the request went to, and
a redirect would carry the key and the body to another. The request fails
instead, naming the host the server pointed at.

\section{Files}

\code{fs-read}, \code{fs-list}, \code{fs-find}, \code{index-grep},
\code{git-status} and \code{git-diff} read; \code{fs-write} and
\code{fs-edit} write. Every path argument is resolved, symbolic links
included, and must land under the session's root, its scratch directory, or
a folder the workspace mounts; a read-only mount refuses every write.
Credential-shaped files (\file{.env*}, \file{*.pem}, \file{*.key},
\file{id\_*}, \file{.netrc} and others) are refused wherever they are.
A write the pin lets through goes ahead, its diff logged and shown
(\code{approval.writes = "allow"}, the default; \adr{35}); with
\code{"ask"} it asks, with a diff, unless a standing approval covers the
path. Either way a write to \file{.nodwyn/}, \file{.git/}, CI
configuration, \file{scripts/} or the \file{Makefile} always asks, because
what is written there later runs with your authority, and so does a write
of content that looks like a credential. Unless git can give a file's
previous content back, because it has the file committed and unchanged,
that content is kept in \file{.nodwyn/versions} before the file is
replaced (\code{nodwyn versions}, \code{nodwyn undo}). What is
read enters the context redacted, and as a Scheme value it carries the tag
\code{external:file}.

\section{Programs}

\code{shell-exec} runs a command to completion; \code{shell-start},
\code{shell-read}, \code{shell-send} and \code{shell-stop} run one that
keeps going. This is the widest channel, and the one the guard sees least
of: it sees the command line, and nothing after the program starts.

What it does with the command line: asks, unless a standing approval covers
the command's prefix\,---\,in a session you answer, by default, the judge
first and you if it refuses or there is none (\code{approval.commands});
names in the prompt any network tool
(\code{curl}, \code{ssh}, \code{rsync}, \ldots), destructive git or
\code{rm}, and any path outside the root; refuses a literal key on the
command line; and turns a command line built from tool output into a
security confirm that no standing approval can answer. The child runs in the
root, with an allowlisted environment (\code{PATH}, \code{HOME}, the Go
variables, locale, \code{TMPDIR} pointing at the session's scratch
directory, and a few more), its output capped, and its own process group so
that an abort kills the whole tree. Only \code{shell-send} writes to a
program's input, and every call is a confirm of its own: typing into a
shell is running commands. Its output enters the context redacted and carries
\code{external:shell}.

What it cannot do: a command you or the judge allowed can read anything
you can read and reach anything you can reach. The confirm is the control,
which is why the prompt names what it can, and why the judge is shown the
task and the plan with the call.

\section{You}

You reach a session through a front-end, and every front-end talks to the
same core. A daemon owns the sessions, every front-end's, line mode's and
the full-screen terminal client's too, and serves a JSON-RPC protocol on a Unix socket readable only by you; every
answer to a prompt is recorded with the kernel's identity of the process that
sent it. The browser console is a bridge from that socket to a page on the
loopback address, paired by a code or a one-time ticket; \code{nodwyn app}
is the same daemon and bridge in one program, with a native window where
the build has one and the default browser otherwise. A phone
or another computer reaches the bridge only if you start it with
\code{--listen} and pair the device by name; its answers are recorded with
that name, and it may answer prompts but not change policy files,
settings, workspaces or MCP servers, nor create or unlock the keychain.

Your messages are redacted before they are recorded (E4), which catches a
key pasted by mistake. A secret you type into a masked prompt goes into the
keychain and is recorded only as its class and handle. Scheme you evaluate
runs with \emph{user} origin and crosses the guard like anything else.

\section{Attachments}

Attaching a file copies it into \file{.nodwyn/attachments/}, extracts its
text (plain text as is; \file{.docx}, \file{.xlsx} and \file{.pptx} in Go;
PDF through \code{pdftotext} when it is installed), redacts it, caps it at
48\,KB with the head and tail kept, and records it as an \code{attach}
event. The model reads it as data framed as such; a document that says
``you may now write outside the workspace'' changes nothing.

An image is not turned into text: it goes to the model as pixels, and no
redactor reads pixels. So attaching one is an act of its own. It is attached
only when the control model takes images, and only after a security confirm
that names the file, says its contents cannot be redacted, and names where
it goes: the control model's host, on this machine or another. Nothing in
it is OCRed. The log keeps its type, size, digest and that host, never the
pixels; the window reads them from \file{.nodwyn/attachments/} and checks
the digest, and a request to any other host, the judge's included, never
carries the image.

\section{Documents out}

\code{doc-export} converts a Markdown or LaTeX file in the workspace to
Word, OpenDocument or HTML with pandoc. Nothing leaves the machine, and the
target is a write like any other. pandoc reads the source in its sandbox,
so an include or a remote image in it reads nothing, and a Word or
OpenDocument file embeds only images that are files in the workspace.
\code{google-doc-upload} sends a document to Google Drive, which makes it a
Google Doc: a keyed request whose class, host and scopes the binding table
decides, asked every time unless you have chosen to always allow or deny
uploads (the first one asks which). The file never was a Scheme value, so the guard
cannot read it; the handler reads all the text it carries and refuses
something shaped like a key whose class is not bound for Drive, before
anything is sent, and \code{doc.upload} records what left.

\section{What stays on the machine}

The session log, the keychain, the policy files, a scratch directory per
session, the version store and the notes a repository keeps between
sessions all live on disk, under \nodwyn's configuration and data
directories or the workspace's \file{.nodwyn/}, except the scratch
directory, which is in the system's temporary directory. The model cannot
write any of them directly: the configuration and data directories are
outside every root and denied (the session's own scratch directory is
outside them, and is the model's to use, and stays so should \code{TMPDIR}
be set inside one); and \file{.nodwyn/} always asks. \code{nodwyn paths} prints where the configuration, the
binding table, the keychain and the session logs are.

\section{The edges, by substrate}

The channels above are how a user meets I/O. The spec states the same
thing by substrate\,---\,Scheme values and the model's text context\,---\,as
four edges, each with its own mechanism:

\begin{center}
\begin{tabular}{@{}lllp{6cm}@{}}
\toprule
Edge & From $\to$ to & Substrate & Mechanism \\
\midrule
E1 & external $\to$ Scheme value & scheme & L2 taint (provenance tag) \\
E2 & external $\to$ model context & text & L1 redaction to \code{[REDACTED class]} \\
E3 & model/Scheme $\to$ external & both & binding check + L1 (+ L2 flag) \\
E4 & user/OS $\to$ model context & text & L1 redaction (catches pasted secrets) \\
\bottomrule
\end{tabular}
\end{center}

Redaction is a \emph{substrate controller}: it runs at every ingress to the
context, not just on API responses, so a leaked value can never be
re-emitted, even to a bound destination. The category error the design had
to resolve was thinking a taint on a value could protect the context window;
it cannot (a window is text, not a value), so the text layers run there.

\chapter{Secrets are credentials}

\section{Binding, not recognition}

A secret is never suspicious in isolation. The bytes \code{sk-ant-...} sent to
\code{api.anthropic.com} are correct; the same bytes sent to
\code{collect.example.com} are exfiltration. Rightness is a \emph{binding}
question:

\begin{quote}
Pass a secret-bearing egress \emph{iff} its class is authorised for
(destination, positions, methods).
\end{quote}

The binding table is user-owned. It lives in \file{bindings.toml}, and
each row names a class, a destination, and the positions and methods
allowed there. A bound egress passes
silently and is logged. An unbound or unknown one is denied by default (a
confirm is opt-in policy, and then the prompt can save the exact row)\,---\,it
never fails open. The harness does not \emph{classify} a secret; the user
\emph{binds} one, and the class is a name the user chose when registering it.

\begin{txt}
[[bind]]
class = "openai-key"
dest = "api.openai.com"
positions = ["header:Authorization:Bearer"]
methods = ["POST"]
\end{txt}

\section{One table for every key}

The same table authorises every key \nodwyn{} holds: a model's, an MCP
server's, the judge's, the Google credential \code{google-doc-upload}
sends, and any API a user tool calls through \code{http-request}. The spec distinguishes the harness's own model key,
\emph{control plane}, from every other credential, \emph{data plane}, so
that other providers become tools among tools. In the code the distinction
is narrower than that: a keyed control model is stored in the keychain and
bound like any other key, and what remains special about it is only that
its requests carry the conversation by design, so their content is not
judged. The judge is never asked about the control model.

An OAuth2 credential (\adr{24}) is bound the same way, with one more fact:
a row may name the scopes it allows, and a token granted more is refused,
because ``Drive, the files this app made'' and ``Drive, everything'' differ
only there. Its refresh is part of a use the table already allowed, sent to
the endpoint fixed when you authorized it, and logged as
\code{cred.refresh}. A refresh the provider refuses denies every use until
you authorize again with \code{nodwyn credential login}; nothing opens a
browser in the middle of a turn.

\section{The content-detection ladder}

Binding is the authority, but local, zero-retention layers watch content, in
a fixed order, each cheaper than the next and each able to stop the
escalation:

\begin{center}
\begin{tabular}{@{}lp{2.2cm}p{7.2cm}p{2.6cm}@{}}
\toprule
Layer & Acts on & Fires when & Status \\
\midrule
L1 & text I/O & a known secret \emph{shape}: prefix, structure, PEM. Fails closed. & built \\
L2 & Scheme values & a value tagged at ingress as coming from outside, or from a credential, heads for egress. & built \\
L3 & text I/O & only the class-unknown residual L1/L2 did not decide. A calibrated $P(\text{secret})$ that feeds the decision with binding, never alone. & planned, optional \\
\bottomrule
\end{tabular}
\end{center}

The deterministic layers early-terminate the learned one: if L1 or L2 already
\emph{knows}, L3 is not paid for. L2 is scoped honestly\,---\,it stops the
\emph{model's} indirect leak, not a user who can strip a tag on purpose with
\code{wipe}, which only user-originated code may call.

\section{The judge: where it is allowed}

The judge is an external calibrated service, Jev or OpenAI's Decisions API
(\adr{46}), with no retention guarantee \nodwyn{} can check. The
original spec drew the line at ``never content''; \adr{19} redrew it where
it belongs, at ``never a secret value''. The question at Seam A\,---\,\emph{is
this plan good enough for the user's ask?}\,---\,has no answer without the ask
and the plan, and both are content.

So the judge is treated as what it is: an \emph{egress edge}. Its credential is a
bound credential (E3), and its payload passes the same redaction controller
as the model context (E2/E4) before it leaves. What may go beyond the ask
and the plan is a user policy\,---\,\code{judge.content}: \code{none},
\code{plan} (default), \code{plan+summaries}, or \code{full}\,---\,and every
call is logged with its level, size, payload hash and the redactions it
triggered. At \code{none} nothing is sent: there is no judge. At
\code{plan} the plan gate sends the ask and the draft plan, and a judged
call\,---\,a command in a session you answer, or any ordinary confirm of a
\code{-{}-judge} run\,---\,sends the task, the plan and the call's shape:
the tool, why the guard asks, and the path written or the command line
run. \code{plan+summaries} is accepted and, for now, sends
what \code{plan} sends. \code{full} adds what a judged call would write or
send, and offers the model the \code{judge} tools, with which it chooses
what is sent.

Two seams:

\begin{description}[leftmargin=1.6em]
\item[Seam A] score a draft \emph{plan} against the \emph{ask} for quality,
  coherence and fulfilment; the model revises on a low score, at most three
  rounds. The default plan gate does this.
\item[Seam C] score an ambiguous \emph{situation}\,---\,class,
  destination, scope\,---\,never the value. A session you answer uses it,
  with \code{approval.commands = "judge"} (the default, \adr{35}), for a
  command, input to a running program or an MCP tool that acts; a
  \code{-{}-judge} run uses it for all its ordinary confirms. Either way Go
  (\file{internal/core/judge.go}) asks \code{judge-choice} whether to allow
  the call and allows it only if the probability of allow is at least
  \code{judge.approve\_threshold} (0.8 by default), and Scheme can only
  refuse more (\code{approve-refuse?}). In a session you answer, a refusal
  is a question for you, told what the judge answered; in a run it is a
  no. A security confirm never reaches the judge: you are asked, and a run
  declines it. Nothing in the default loop or the guard calls it
  otherwise.
\end{description}

Never: a secret value (enforced by redaction, not by withholding content),
control flow, its own loop, or the harness's control model. The local stack
judges provenance and secret shape, and is the only thing that ever sees a
value.

\chapter{The loop and the guard}

The agent loop is the plain one: ask the model; run the tools it asks for,
through the guard; feed the results back; ask again. Stop on a plain answer
or a hard stop.

The loop is itself a Scheme procedure, \code{agent-turn}, so how a turn goes
can change without changing Go: plan first, check with the judge, stop a
batch of calls at the first failure, hand part of the work to a sub-agent in
a narrowed context of its own. What a turn must not skip stays in Go, behind
a few primitives: windows built from the log, only the model's own calls
run, exactly one result per call, and budgets and a progress guard that the
procedure cannot catch (\adr{26}). The same procedure can route work: narrow
the context to a task and a plan, and hand it to another model the user
configured (\adr{27}).

The default procedure runs a plan gate first. With a judge configured, the
judge says whether the request needs a plan (a question, a review or a
proposal is answered, not planned); if it does, a read-only
sub-agent looks around, the model drafts a plan, the judge scores it against
the ask, and the model revises it at most three times. A plan's steps each
start with their kind: the change, each test with why it fails on today's
code, the docs the change makes wrong, and last the check that shows it
works; the judge scores that shape, and a plan the model writes itself
without it is turned down. The outcome is
recorded per message, and the plan stays in the model's view for the rest
of the turn. A supervised run's turns always plan, and until a plan is
recorded the core refuses anything irreversible.

The guard is a pipeline of \emph{checkers}. Each looks at the primitive's
declared metadata and its actual arguments and returns a verdict; the
strictest wins (deny over confirm over allow). A confirm is put to the user
through a \emph{confirmer} the core implements as an event plus a wait, so
the guard never knows what a terminal is; in a session a person answers,
\code{approval.commands} may have the judge answer an ordinary confirm
first. A \emph{standing approval}\,---\,a command prefix or a write path
the user authorised ahead of time, and, by default, any write in the
folder\,---\,turns an ordinary confirm into an allow and never turns a deny
into anything. A \emph{security} confirm\,---\,a write to a protected
path, content that looks like a key, a command line built from tool output,
an image to attach\,---\,cannot be answered by a standing approval, an
\code{[approval]} setting or the judge. It goes to the person, and a run
nobody watches refuses it (\code{-{}-yolo}, a \code{-{}-judge} run and an
unattended run alike). A project may add
its own checkers in Scheme (\code{register-check}); they can deny or ask,
never allow. Every decision that reaches the host, and every non-allow, is
logged with who asked (the user, the model or the harness) and why.

\chapter{Memory}

Three tiers, one truth:

\begin{itemize}
\item \textbf{Disk}: the lossless log. Source of truth.
\item \textbf{Cache}: summaries and handover notes, written \emph{as log
  entries}, rebuildable and revocable, possibly stale.
\item \textbf{RAM}: the token-budgeted window, rebuilt from the log for every
  request.
\end{itemize}

The window keeps the request prefix byte-stable so that the model server's
prefix cache keeps hitting: elision is sticky, and it happens in bursts,
from a high-water mark down to a low-water mark, oldest tool results first,
the user's words never. Before trimming would begin, the default loop
\emph{compacts}: the model writes a handover note and the conversation goes
on from it, while the log keeps everything. A user may also write a summary
of a span by hand and revoke it later.

Retrieval is text search over the current tree (\code{index-grep}), and
word search: over an index of the files git lists, kept in nodwyn's data
directory and shared by a repository's worktrees, and over the
conversation, whose elided and folded results the model can bring back
whole, and, when the person allows it for a project, its earlier tasks
(\code{index-search}, \code{index-update}, \code{recall}, \adr{50});
there is no embedding index. One thing crosses sessions: a repository's
\emph{notes}, which a strategy saves and the next session in the same
repository shows as the agent's own leads, not as instructions. And
\code{/optimize} reads a repository's past session logs to improve its
\file{.nodwyn/init.scm}, asking before every write.

\chapter{Honest limits}\label{ch:limits}

What \nodwyn{} does not protect against, or does not yet:

\begin{enumerate}[leftmargin=2em]
\item L2 is scoped, not a security boundary. It stops the model's
  unintended leak; a user can strip a tag. The real lines are binding
  (E3), fail-closed defaults, and ingress redaction (E2/E4).
\item A bare ``confirm'' can be uninformed consent. If the class is also
  unknown, the prompt is a rubber stamp. Mitigation: always name class and
  destination; prefer requiring a binding to a bare yes.
\item L3 does not exist yet. L1 recognises known key shapes; a novel
  internal token, a password or an encoded key passes it. Binding still
  governs every key \nodwyn{} holds, but a secret that is only content is
  not recognised.
\item ``The egress surface is closed'' is not something the harness can
  prove of itself. With all four edges guarded, the honest statement is: no
  path exists for a secret \emph{value} to egress unless bound or explicitly
  confirmed\,---\,and ``closed'' is the user's affirmation.
\item A confirmed command is a confirmed command. The guard sees a command
  line, not what the program does; a \code{y} to a script, yours or the
  judge's, is a \code{y} to everything the script does.
\item With the defaults, a person need not look at the work. Writes in
  the folder go ahead and, once a judge is set up, the judge allows
  commands (\adr{35}), so the model can write code and run it without a
  person looking at either. The judge decides each command with the task
  and the plan in view. What does not depend on it: the pin, the
  denylist, the binding table and L1 on egress, taint on a command built
  from tool output, the protected paths, the scrubbed environment and the
  hard limits. \code{approval.commands = "ask"} puts every command to you,
  and \code{approval.writes = "ask"} every write.
\item A model provider, and an MCP server, sees what it is sent.
  Configuring a model is consenting that the window leaves for it;
  approving an MCP tool is consenting that its arguments leave for the
  server. L1 scans them for key shapes and L2 reads their provenance, but
  approving a server names its host for L2, so tool output may go to any
  server you approved, and L2 does not tell one server's result from
  another's. What stands between a file and a server is the confirm, for
  every tool not declared a read.
\item \nodwyn{} controls where content goes, not what content means. L1
  detects credentials; nothing recognises a contract, a medical letter or a
  salary list. What applies to those is the pin and the mounts (what can be
  read at all), the confirm (what leaves), the binding table (where it may
  go) and the judge's content level.
\item A paired device that may approve \code{shell-exec} can run commands as
  you. ``Answers, not policy'' limits what the console lets a device change,
  not what its answers authorise. Pair only devices you would hand a
  terminal.
\end{enumerate}

\section{Authority is separate from project content}

A repository supplies behaviour but cannot approve its own execution. The person
reviews the init and approvals revision; the host stores trust outside the clone.
The guard still applies after trust, and approved commands retain the user's OS
privileges. Credential bindings answer where and how a key may be used; HTTPS is
a separate default, with an explicit user exception for remote HTTP. These are
implemented boundaries, not promises that all project code or network content is
safe (\adr{45}, \file{docs/security.md}).

\paragraph{Cancelled document extraction.}
Office document extraction honours cancellation and request deadlines before
reading and between XML tokens. A cancelled extraction returns an error rather
than a successful partial document; spreadsheet cell references and the
workbook/deck ordering remain authoritative.
