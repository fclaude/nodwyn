\part{Using \nodwyn}

\chapter{Install and configure}

\begin{sh}
make build                       # bin/nodwyn and bin/nodwyn-egress
make build-webview               # the same, with a native window for nodwyn app
make app                         # bin/Nodwyn.app for macOS
make promote                     # accept + selfcheck, then ~/.local/bin/nodwyn-stable
\end{sh}

Building needs Go~1.26 or newer (\adr{33}). Working on \nodwyn{} itself
also needs \code{staticcheck}, and you should use \code{nodwyn-stable} for
real work and \file{bin/nodwyn} only to test a change to \nodwyn{}.
\code{nodwyn app} opens a native window only in a build with the
\code{webview} tag, which needs cgo and the platform's web view (WebKitGTK
on Linux); \code{make build} leaves it out and \code{nodwyn app} then
opens your browser. \code{make promote} builds \code{nodwyn-stable} with
the tag wherever it can, and its version is the commit it was built from.
\code{nodwyn-egress}, built static for Linux, is the proxy a contained MCP
server reaches the network through; \nodwyn{} looks for it next to its own
executable, where \code{make promote} installs it.

\code{nodwyn paths} prints where \file{config.toml}, \file{bindings.toml},
the keychain and the session logs are. \file{mcp.toml} sits beside
\file{config.toml} in the configuration directory; a repository's notes and
the sessions' scratch directories are in the data directory, beside the
session logs.

\section{config.toml}

There is no built-in model: \code{[control]} names the one \nodwyn{} talks
to, and without it \nodwyn{} prints the table to add. The first run of
\code{nodwyn app} asks for it and writes it for you. The rest has defaults:

\begin{txt}
[servers.local]                     # where models are, and their key
provider = "ollama"                 # or "openai": any chat-completions server
url      = "http://localhost:11434"

[servers.openai]
provider   = "openai"
url        = "https://api.openai.com/v1"
credential = "openai-key"           # a keychain class, for a keyed server

[control]
server = "local"
model  = "qwen3:8b"

[models.coder]                      # another model a strategy may ask by name
server = "openai"
model  = "gpt-5.1-codex"

[window]
high_water        = 61440   # trim above this (estimated tokens); grows with
low_water         = 30720   #   a larger control context unless you set it
max_result_tokens = 3072    # larger tool results are shown head and tail
output_reserve    = 16384   # also the cap on each reply

[policy]
unbound        = "deny"     # or "confirm" for keyed egress no binding covers
allow_commands = []         # standing approvals, global
allow_writes   = []

[approval]                  # what a session you answer does without asking
writes   = "allow"          # or "ask"
commands = "judge"          # or "ask", or "allow"

[loop]
request_timeout = "30m"
shell_timeout   = "10m"

[budget]                    # per turn: "soft" asks, "hard" stops
tool_calls_soft = 500       # a soft limit left unset is its hard one,
tool_calls_hard = 500       #   so nothing asks until you set one lower
tokens_soft     = 10000000
tokens_hard     = 10000000
actions_soft    = 200
actions_hard    = 200
wall_soft       = "4h"
wall_hard       = "4h"
# cost_soft     = 2.0       # US dollars for the whole task; off unless set
# cost_hard     = 10.0

[jev]
content = "plan"            # none | plan | plan+summaries | full
approve_threshold = 0.8     # the judge allows a call at or above this
# price_input   = 0.5       # US dollars per million tokens: the judge reports
# price_output  = 2.0       #   its tokens, never its cost

[docs]
google_credential = "google"  # the class google-doc-upload sends; "" for none
google_upload = "ask"         # ask | allow | deny; unset, the first upload asks

[mcp]
# runtime = "podman"        # or "docker"; unset: podman if on PATH, else docker
# egress = "..."            # nodwyn-egress; unset: next to the nodwyn binary
\end{txt}

A provider offers many models at one address under one key, so a server
holds \code{provider}, \code{dialect}, \code{url} and \code{credential},
and its models name it; a model may give them itself instead. The app saves a
server the first time you choose a model on it, and after that lists the
models the server offers.

Chat Completions servers may interpret extensions differently. For Cerebras,
set \code{dialect = "cerebras"} beside \code{provider = "openai"} in its
server table, or on a model that names no server, before starting \nodwyn{}.
It sends prior assistant thinking as \code{reasoning}; the default,
\code{"compatible"}, keeps \code{reasoning\_content}. For OpenAI itself,
\code{dialect = "responses"} sends each request to its Responses API
instead, where a reasoning model such as gpt-6.1-sol takes an effort beside
tools, which it refuses on chat completions; there a reply's thinking is not
sent back, and nothing is stored on OpenAI's side. Unknown dialects
and dialects on Ollama are refused. Settings sets it with the rest of a
provider, where you can see it before saving, and keeps it when it saves
another model on that server. The choice changes neither the key's binding
nor what the conversation log records.

A reasoning model takes an effort, how hard it is asked to think. A provider
decides which words it accepts, and may refuse a request that carries one it
does not know, so a model takes an effort only if its entry says which:
\code{efforts = ["low", "medium", "high"]}, and \code{effort = "medium"} for
the one a conversation starts with. Nothing is inferred from a model's name.
The word goes out as \code{reasoning\_effort} to a chat-completions server and
as \code{think} to Ollama (\code{["off", "on"]} for a model that thinks or does
not), and the log records it on each request (\adr{41}).

In the console, Settings $\to$ Models does all of this without the file:
providers with their address, dialect and key, and whether each can be used and
why not; a test request that says whether the key was accepted; the models to
choose between, each with its efforts and its own settings (its context
length, its prices, whether it takes images); and the default model and effort
new tasks start on. Under the message box of the New task window, a Model and an
Effort select change what the next message is answered with. In a conversation
they are tucked behind a compact model-and-effort summary: click it, or focus it
and press Enter, to expand them. Warnings and change notices remain visible
when collapsed, and a task that needs a model chosen opens the selects for
you. A change made while a response is running waits for it, and the
page says so; an unchanged running response shows no change notice.
A task whose model has gone from the list asks nothing until you
choose one for it.

A model may also set \code{num\_ctx} (sent to Ollama; for the model a
conversation is on it also sizes the window, and OpenAI's and Cerebras' model
lists do not say it, where OpenRouter's does) and \code{keep\_alive} (Ollama),
\code{max\_output} and \code{output\_field} (servers that need them),
\code{temperature} and \code{seed}, \code{cache\_control} (\code{"ephemeral"}
or \code{"1h"}: a Claude model caches its prompt only when the request asks, and
nothing is inferred from its name; \adr{9}), and \code{price\_input},
\code{price\_cached\_input} and \code{price\_output}: its prices in USD per
million tokens, from which a request's cost is estimated when the provider
does not report it (cached input unset is priced as input). Each request
records the settings it was sent with, so \code{nodwyn replay --window} can
rebuild it. These settings are the model's own: \code{[control]} names the
default model, and each one it leaves unset comes from the model's
\code{[models.NAME]} entry, as its efforts do, so the model has the same
settings whether it is the default or chosen in a picker (\adr{41}, amended).
A chat-completions model is taken to read images unless its entry says
\code{vision = false}: a provider that cannot read one refuses that request,
and the turn says so (\adr{22}, amended). Ollama reports it itself.

\chapter{Ways in}

\begin{description}[leftmargin=2.2em]
\item[\code{nodwyn}] Line mode in the current directory: the session runs
  in this process, and ends with it. Scriptable; \code{--no-confirm}
  answers every confirm with no.
\item[\code{nodwyn tui}] The full-screen terminal client, in its own
  process or attached to a daemon with \code{--socket}.
\item[\code{nodwyn daemon}] Owns sessions over a private Unix socket, so
  they outlive the client that started them. Everything below talks to it.
\item[\code{nodwyn ui}] The browser console for a running daemon: tasks,
  approvals inline with their diffs, plans, budgets, changes and their
  history, attachments, notes; Connections for MCP servers, Workspaces for
  folders, Settings for what a task does without asking (Approvals), its
  limits, the models and their settings, the judge and the keychain. Every task
  it starts is a chat, and a long request is a message like any other
  (\adr{35}); it starts no runs, but shows one that \code{nodwyn run}
  started. Its sidebar lists tasks under their folders, the latest active
  first; a task can be named, and a closed one archived or deleted
  (\adr{39}). A task started \textbf{In a worktree} works in a git
  worktree of its own, on its own branch, so several can work on one
  repository at once (\adr{34}). Switching back to an open task shows it
  as it was, without reading its conversation again.
  Streamed text and thinking are joined for the next display frame, keeping
  the heading and detail panels in place. A task kept off screen catches
  up when shown; replies and questions flush preceding fragments at once.
  Reading earlier text keeps your scroll position.
\item[\code{nodwyn app}] The daemon, the console and a window in one
  program. It attaches to a daemon if one is running, and otherwise serves
  one itself until you close it.
\item[A phone] \code{nodwyn ui --listen ADDR} serves other devices as well.
  Each pairs with the printed code and a name, may send messages and answer
  prompts, and may not change settings, policy files, the keychain,
  workspaces or MCP servers, or delete a task. \code{nodwyn devices revoke NAME} unpairs one.
\end{description}

\chapter{A session}

\begin{sh}
$ cd ~/src/your-repo
$ nodwyn-stable
nodwyn session 20260930T101500Z-1c2d3e4f
repo  /home/you/src/your-repo
tools doc-export fs-edit fs-find fs-list fs-read fs-write git-diff git-status
      index-grep plan-step plan-write read-definition second-look shell-exec
      shell-read shell-send shell-start shell-stop
:h for commands

you> read main.go and explain the startup sequence
\end{sh}

At the prompt:

\begin{center}
\begin{tabular}{@{}ll@{}}
\toprule
\code{:q} & quit (writes \code{session.end}) \\
\code{:log [n]} & last $n$ log events \\
\code{:tools} & tools offered to the model \\
\code{:allow} & standing command and write approvals in effect \\
\code{:eval EXPR} & evaluate Scheme yourself (user origin) \\
\code{:thinking} & toggle showing the model's redacted thinking \\
\code{/compact [what to keep]} & compact the conversation into a handover note now \\
\code{/optimize [n | ids] [focus]} & learn from past sessions; improve \file{.nodwyn/init.scm} \\
Ctrl-C & abort the running turn; at the prompt, exit \\
\bottomrule
\end{tabular}
\end{center}

The two slash commands work in every client. While a turn runs, line mode
prints the reply once it is complete, a card per tool call, guard flags, and
a usage line per model request, as the full-screen client and the console
do:

\begin{center}
\code{12,400$\to$800 tok \textperiodcentered{} 78\% cached
\textperiodcentered{} \$0.012 \textperiodcentered{} 3.2s}
\end{center}

Prompt and output tokens always; the share of the prompt the provider read
from its cache, and the request's cost, only when known (a cost estimated
from the model's configured prices is marked $\approx$); the time only when
the server reports it. A budget checkpoint says what the turn has cost so
far, ``at least'' when some requests had no known cost.

The full-screen client takes the same commands and adds inspectors:
\code{:plan} shows the turn's plan gate, its plan, and each step (each
starts with its kind: \code{Change:}, \code{Test:}, \code{Docs:} or
\code{Check:}) as the model marked it, done (\code{[x]}), skipped (\code{[-]}) or not yet
(\code{[ ]}), with its note; \code{:budget} shows the configured limits,
what the latest turn's model requests cost as far as known, and its
checkpoints; \code{:replay}, \code{:bindings} and \code{:friction} show
the transcript, the binding table and \file{docs/friction.md}.

\code{nodwyn --resume ID} continues a session in the same log, with the
configuration, bindings, approvals files and \file{init.scm} as they are
now. Session-only approvals are not restored, and a tool call that was
running when the process died is never rerun: it is marked ``outcome
unknown'' so the next turn can look before it retries.

\chapter{Confirms}

A tool call the guard neither allows nor denies outright is a
\emph{confirm}. In a session you answer\,---\,the console's, the
full-screen client's and line mode's\,---\,\code{[approval]} in
\file{config.toml}, which the console sets in Settings \textrightarrow{}
Approvals, decides which of them go ahead without you (\adr{35}):

\begin{description}[leftmargin=2.2em]
\item[\code{writes = "allow"}] the default. A write the pin lets
  through\,---\,in the repository or folder, the scratch directory or a
  mount opened for writing\,---\,goes ahead. Its diff is logged and shown
  in the transcript, and its previous content is kept
  (Chapter~\ref{ch:undo}). \code{"ask"} makes every write stop for you,
  with its diff.
\item[\code{commands = "judge"}] the default. A command no standing
  approval covers, input to a running program, or an MCP tool that acts is
  put to the judge first, which is shown the task, the turn's plan and the
  call. If the judge allows it, it runs, recorded with the judge as the one
  who answered. If the judge refuses or fails, you are asked, and the
  prompt says what it answered. Without a judge (no \code{jev-key} stored,
  \code{jev.content = "none"}, or a locked keychain) you are asked.
\item[\code{commands = "ask"}] you answer each one.
\item[\code{commands = "allow"}] they run, recorded with the actor
  \code{setting}.
\end{description}

Some confirms neither setting answers, and they come to you, where a run
nobody watches declines them: a security confirm (below), a write while
\code{writes} is \code{"ask"}, a call that carries a credential or
proposes a binding, and an upload. Standing approvals (below) apply first,
as before. \code{writes} applies to every session, a run's included; the
flags of \code{nodwyn run} and \code{-{}-no-confirm} decide the other
confirms of their sessions as before. A confirm that reaches you gives a
reason and, for a write, a diff; this one is a write with \code{writes =
"ask"}:

\begin{txt}
--- confirm: fs-edit ("internal/x.go" "old..." "new...")
  * fs-edit is irreversible
  * changes internal/x.go
  --- internal/x.go
  +++ internal/x.go
  @@ -12,3 +12,3 @@
  ...
allow? [y/N/a=always under internal//t=all writes this turn]
\end{txt}

Several changes to one file come as one \code{fs-edit} call with a list of
edits (\adr{38}): it asks once, its diff is the whole file's with every edit
applied, and nothing is written unless every edit applies. The header then
shows the call in Scheme's positional form, the list after an empty
\code{old}, an empty \code{new} and \code{\#f}.

\begin{description}[leftmargin=2.2em]
\item[\code{y}] once.
\item[\code{N}] (or anything else) no. The model is told
  \code{denied: not confirmed by the user} and moves on.
\item[\code{a}] yes, and a \emph{standing approval for this session}: the
  command prefix (\code{go test}, \code{rg}) or the write's directory
  (\code{internal/scheme/}). Not persisted. A command made standing this
  way is not put to the judge again.
\item[\code{t}] writes only: yes, and every further write \emph{until this
  turn ends}. For a task you intend to review with \code{git diff}
  afterwards. Each auto-approved write's diff is logged and shown dimmed.
\item[\code{b}] keyed requests only, when \code{policy.unbound =
  "confirm"}: yes, and save this exact binding row to \file{bindings.toml}.
\end{description}

Read the reason lines. ``command line names a path outside the repository''
and ``uses the network tool curl'' are the guard telling you what a
\code{y} would do. A \emph{security} confirm\,---\,a write to \file{.nodwyn/},
\file{.git/}, CI configuration, \file{scripts/} or the \file{Makefile},
content that looks like a key, a command line built from tool output, an
image to attach\,---\,offers only \code{y} and \code{N}. No standing
approval and no \code{[approval]} setting answers it, and \code{-{}-yolo},
a \code{-{}-judge} run and an unattended run all decline it.

\section{Standing approvals}

\begin{txt}
# ~/.config/nodwyn/config.toml           (global)
[policy]
allow_commands = ["go test", "go build", "git status", "git diff", "rg"]

# <repo>/.nodwyn/allow.toml              (per repository, tracked)
commands = ["make lint", "make test"]
writes   = ["internal/", "docs/"]
\end{txt}

Prefixes match argv tokens: \code{"go test"} matches \code{go test ./...}
and \code{/usr/local/go/bin/go test}, not \code{go build}. Denies still
apply\,---\,only the confirm is waived\,---\,and every use is logged with the
prefix as reason. Keep command approvals to commands that only read or
test: nothing that commits, pushes, deletes or reaches the network. Write
approvals matter while \code{approval.writes} is \code{"ask"}; by default
every write in the folder already goes ahead.

\chapter{Keys, models and the judge}

\begin{sh}
nodwyn keychain init                       # once; asks for a passphrase
nodwyn-stable                              # then, at the prompt:
:eval (credential-register "openai-key")   # masked input
\end{sh}

The console stores keys without a terminal: Settings the model providers',
Connections an MCP server's, each with its one binding row, and Connections
\textrightarrow{} Credentials any key, with the host it may go to, and
OAuth2 accounts. A key can also be registered as above.
When the app starts with a locked keychain, Home opens the unlock form and
focuses its masked password field. Startup refreshes keep the field and the
passphrase being typed there, rather than moving typing into chat; a failed
unlock returns focus to the password for another attempt.
\code{nodwyn keychain init -{}-no-passphrase} makes a keychain that opens
without asking, which is as safe as its file permissions and no safer. A key is
stored under a class you name, and it goes nowhere until a row in
\file{bindings.toml} allows it:

\begin{txt}
[[bind]]
class = "openai-key"
dest = "api.openai.com"
positions = ["header:Authorization:Bearer"]
methods = ["POST"]
\end{txt}

A keyed model names the class as its \code{credential}; the binding is
checked on every request and recorded as \code{egress.check}. The judge
works the same way with the class \code{jev-key}, bound to its host: the
console's Connections page keeps a Judge card at the top of its
Credentials, with one field for the key when none is stored, and the
binding it writes is the judge's own (its host, Bearer token, \code{POST}).
Once that key exists, the default loop's plan gate runs before each message,
and the judge answers commands before you are asked
(\code{approval.commands = "judge"}, the default). Set
\code{jev.content = "none"} to send it nothing, or \code{"full"} to
give the model the judge as tools (\code{judge-noul}, \code{judge-score},
\code{judge-choice}) in sessions started after the key was stored. A daemon holds the
keychain for every session it opens: unlock it once, from its terminal or
the console, and sessions opened afterwards can use it.

A service that uses OAuth2, such as Google Drive or an MCP server behind a
login, gets a credential of kind \code{oauth2}: register \nodwyn{} as an
OAuth client with the provider, then authorize it in the browser:

\begin{sh}
nodwyn credential add --oauth2 google --client-id ID --scopes drive.file
nodwyn credential                     # list: kind, scopes, expiry
nodwyn credential login google        # after the provider refused a refresh
nodwyn credential revoke google       # at the provider, and here
\end{sh}

It is bound like any key, and its row may name the scopes it allows
(\code{scopes = [...]}), so a token granted more is refused. The keychain
refreshes the token just before a use the binding allowed, the session logs
\code{cred.refresh}, and a confirm names the scopes with the class and the
destination. \code{--oauth2 custom} with \code{--auth-url} and
\code{--token-url} covers a provider \nodwyn{} has no profile for.

\chapter{Connecting an MCP server}

Connections, in the console, adds a server. A remote one needs its address
(\code{https}, or plain \code{http} to this computer only), and, if it needs
one, a key, which goes into the keychain with a binding for that host only.
Then:

\begin{enumerate}[leftmargin=2em]
\item \textbf{Review} the tools the server offers: their names and the
  start of each description. Their input schemas and the server's own
  hints are part of the tool list you approve, but the console does not
  show them.
\item \textbf{Declare} what each tool you want does: \emph{reads}, or
  \emph{changes things}. Leave it undeclared and every call asks, as if it
  both sent data out and could not be undone.
\item \textbf{Turn on} the tools the model should see. Nothing is on until
  you choose.
\item \textbf{Approve} the tool list, which records its hash, and choose the
  workspaces where the server is offered.
\end{enumerate}

The result is \file{mcp.toml} in the configuration directory (Chapter
\ref{ch:io} shows one). New sessions in those workspaces offer the tools as
\code{server\_\_tool}; a session already open keeps its tool list. If the
server's tool list changes, new sessions withhold all of its tools until you
review it again. Approval, edits and removal are refused from a paired
remote device.

\section{A server on this computer}

\nodwyn{} does not run a third-party server as a process of yours. A local
server is \emph{contained}: \nodwyn{} runs it in a container, with podman or
docker, from an image pinned by its digest. Connections asks for the image,
the hosts it may reach (none, or a list), the workspace folders it sees, and
the variable it reads its key from, if it needs one:

\begin{txt}
[[server]]
name = "notion"
transport = "container"
image = "ghcr.io/example/mcp-notion@sha256:..."   # a tag is refused
network = ["api.notion.com"]                      # [] is no network
mounts = ["docs"]                                 # read-only; "out:write"
credential = "notion-key"
position = "env:NOTION_TOKEN"
\end{txt}

A task never downloads code: \code{nodwyn mcp pull notion}, or Pull on the
server's page, fetches the image by its digest, and \code{nodwyn mcp} says
which images are here. The container gets no capability, a read-only root,
none of your environment and none of your files beyond the folders listed.
With no network it has none at all; with hosts, its only way out is
\nodwyn{}'s egress proxy, which lets through those hosts and nothing else,
and the session log records every attempt (\code{mcp.egress}). Its key goes
in only if it is bound for every one of those hosts, as the variable named
(\code{env:NOTION\_TOKEN} in \file{bindings.toml}). A confirm names the
contained server and what it can reach. The containers are removed when the
task closes.

\chapter{Workspaces, attachments and undo}\label{ch:undo}

A session's root is the directory it was started in. A workspace can also
\emph{mount} other folders, read-only or writable. The mounts are yours,
kept with the workspace's name in \file{workspaces.toml} in the config
directory, never in the folder, so a repository someone else commits cannot
mount anything (\adr{22}):

\begin{txt}
[[workspace]]
name = "Contracts"
path = "/home/me/work/contracts"

[[workspace.mount]]
path = "/home/me/Reference/contracts"
access = "read"
\end{txt}

The console's Workspaces page adds, names and removes folders and edits
their mounts; removing one forgets its name and mounts, never the folder.
Attachments come in through the console's composers (or
\code{session.attach} over the protocol); Chapter~\ref{ch:io} says what
happens to them.

Where git is not the undo, \nodwyn{} keeps a file's previous content in
\file{.nodwyn/versions} before replacing it. Git is the undo for a file it
has committed and unchanged; outside a git work tree, and for a file with
uncommitted changes, an untracked one or an ignored one inside it,
\nodwyn{} keeps the version, so \file{.nodwyn/versions} appears in git
repositories too, with a \file{.gitignore} that keeps it out of
\code{git status}. Each write in a git work tree asks git
(\code{git status}) which case it is. \code{nodwyn versions FILE} lists the
kept versions, \code{nodwyn undo FILE} puts back the newest, and the
console's Restore puts back any of them. A Restore is a write like any
other: it goes ahead without asking unless \code{approval.writes} is
\code{"ask"}, and what it replaces can be put back the same way.

\chapter{Documents out}

The model's \code{doc-export} turns a Markdown or LaTeX file into Word
(\file{.docx}), OpenDocument (\file{.odt}) or HTML, picked by the target's
extension. It needs pandoc 2.15 or later on \code{PATH}; without it the
tool says what to install. The target is a write like any other: it goes
ahead in the folder unless \code{approval.writes} is \code{"ask"}, when
the confirm shows source, target and formats and a standing write approval
covers it; where git is not the undo, the previous version is kept. pandoc
reads the source in its
sandbox, so an include or a remote image in it reads nothing, and a
\file{.docx} or \file{.odt} embeds only images that are files in the
workspace.

PDF is not among them: a TeX engine reads any file and runs programs when a
document asks. A LaTeX build stays \code{shell-exec} running
\code{latexmk}, as this book's is (\code{make book}), with a standing
approval if you choose to give one.

\code{google-doc-upload} sends a \file{.docx}, \file{.odt}, \file{.html} or
\file{.txt} to Google Drive as a new Google Doc and returns its link. It
needs the OAuth2 credential above, whose default scope \code{drive.file}
is enough, bound to Drive's upload host:

\begin{txt}
[[bind]]
class = "google"
dest = "www.googleapis.com"
positions = ["header:Authorization:Bearer"]
methods = ["POST"]
scopes = ["https://www.googleapis.com/auth/drive.file"]
\end{txt}

Sessions started after the credential was stored offer it. How an upload
is handled is your setting, \code{google\_upload} in \code{[docs]}, and
until you choose, the first upload asks you which:

\begin{itemize}
\item \emph{Allow by hand} (\code{ask}): every upload asks, naming the
  file, its size and the destination. It is a security confirm, so no
  standing approval covers it, \code{approval.commands} does not answer it,
  and \code{-{}-yolo}, \code{-{}-judge} and an unattended run never upload.
\item \emph{Always allow} (\code{allow}): uploads go without asking,
  in a run too, wherever the binding table lets them. Only the computer
  \nodwyn{} runs on can choose it, never a paired phone.
\item \emph{Deny} (\code{deny}): uploads are refused, and later sessions
  do not offer the tool.
\end{itemize}

The answer goes into \file{config.toml}, is logged as
\code{setting.change} with who gave it, and holds for every session;
Settings in the console changes it. A run with nobody to ask declines an
upload while the setting is unset. A
document holding something shaped like a key whose class is not bound for
that host is refused before anything is sent, and each upload is logged as
\code{doc.upload}: file, size, hash, destination and the document's id.
\code{[docs]} in \file{config.toml} also names another credential class
(\code{google\_credential}) or endpoint (\code{google\_upload\_url}).

\chapter{Budgets and runs}

A turn has hard limits on tool calls, reported model tokens, irreversible
actions and wall time (\code{[budget]}): by default 500 tool calls, ten
million tokens, 200 actions and four hours. At a hard limit the turn stops.
Each also has a soft limit, Settings' ``ask at'', which by default is the
hard one, so no checkpoint interrupts a turn (\adr{35}). A soft limit the
file leaves unset follows its hard one, so lowering a hard limit moves the
checkpoint with it. Set a soft limit lower to have the turn stop there at a
\emph{checkpoint}: \code{y} doubles the soft limit up to the hard one,
\code{n} stops, a number or a duration sets a new soft limit. A checkpoint
never approves a tool. The flags \code{--max-tool-calls},
\code{--budget-wall}, \code{--budget-tokens} and \code{--budget-actions}
set the hard limits for one invocation.

A spend limit is yours to set, and off unless you do: \code{cost\_soft}
and \code{cost\_hard} in \code{[budget]}, in US dollars, or
\code{--budget-cost} for one session or run. It counts what the whole task
has cost, every turn and a resumed session's history included, not one
turn. Past the soft limit a checkpoint asks (a new soft limit is in dollars,
and holds for later turns); at the hard one the task stops, a run ends
\code{limited}, and nothing reaches the model until you raise it. It counts
only costs it knows, reported by the provider or priced from the model's
\code{price\_*}; the first turn with a request it cannot price says so.

A turn also stops if the model
repeats an identical call four times in a row, retries a denied call three
times, or gets ten tool errors in a row.

A long request is a message like any other: the turn goes on until the
model answers, a command needs you (there is no judge, or it refused), a
security confirm comes up, or one of the stops above ends it.

A \emph{run} is not a way of working in the console. \code{nodwyn run} is a
batch tool for scripts and benchmarks: it carries a task to its end with no
conversation, submitted to a daemon:

\begin{sh}
nodwyn run --task task.txt --repo . --budget-wall 2h --max-turns 20
nodwyn run status SESSION
nodwyn run stop SESSION
nodwyn run resume SESSION
\end{sh}

For a run, \code{--budget-wall} is the deadline of the whole run, not of
one turn. Each turn of a run must record a plan before it may do anything
irreversible, and in a supervised run a person says yes at a checkpoint
between turns. A run
ends when the model's reply ends with the line \code{NODWYN\_RUN\_COMPLETE},
which is its claim, not proof. \code{--yolo} answers a run's ordinary tool
confirms with yes; it does not answer security confirms, and it does not
continue the run between turns. \code{-{}-judge} has the judge answer them
instead: it is shown the task, the plan and the call (at
\code{jev.content = "full"}, also what the call would write or send), and
the call runs only if the judge's probability of allow is at least
\code{jev.approve\_threshold} and the project's \code{approve-refuse?}, if
it defines one, does not refuse it. It needs a stored \code{jev-key},
excludes \code{--yolo}, and declines security confirms. Use either on a
throwaway checkout: the guard makes an unattended run survivable, not safe.
\code{-{}-unattended} goes further: nobody answers at all. Tool confirms
are declined unless a standing approval covers them (by default every
write in the folder is one), answered yes with
\code{--yolo} or put to the judge with \code{-{}-judge}; a soft budget
checkpoint goes on to the hard limit; and the run goes on to its next turn
only after a turn that marked a step of its plan done. A resume restores
none of these flags: give them to \code{nodwyn run resume} again.

The console does not start or resume runs. It shows a run started
elsewhere, and its Stop ends it; a message sent afterwards goes on with the
task as a chat.

\chapter{Building \nodwyn{} with \nodwyn}

\begin{enumerate}[leftmargin=2em]
\item \code{nodwyn-stable} in this repository; \code{:tools} lists
  \code{go-test}, \code{git-log}, \code{grep-repo}, \code{read-adr},
  \ldots
\item Give it tasks that name the file, the pattern to follow and the test
  to add, and ask it to run \code{go-test} on the package.
\item Review the diffs. By default each write goes ahead and is shown
  with its diff; read them as they come, or with \code{git diff} at the
  end. With \code{approval.writes = "ask"}, review each at the confirm, or
  answer \code{t} and review at the end. An \code{fs-write} of a whole
  existing file deserves suspicion; an \code{fs-edit} rarely does.
\item When it gets in the way, hand-edit, and add one line to
  \file{docs/friction.md}.
\item \code{make accept} before committing. You commit; there is no commit
  tool.
\item \code{make promote} when a change's acceptance is green.
\end{enumerate}
