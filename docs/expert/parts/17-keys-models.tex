\chapter{Keys, bindings and the network}
\label{ch:keys}

This chapter is about everything that leaves your machine on purpose: model
requests and what they cost, keyed APIs your tools call, the judge, and MCP
servers.

\section{The keychain}

Keys live in an encrypted file, the keychain, unlocked with a passphrase
you choose (not recoverable; the console asks for at least 8 characters). Create it once:

\begin{sh}
nodwyn keychain init          # or: the app's Settings page
nodwyn keychain passphrase    # change it later; --remove leaves none
\end{sh}

When the app starts with a locked keychain, Home opens the unlock form and
focuses its masked password field. Startup refreshes preserve that field and
what is being typed, rather than moving typing into chat. A failed unlock
returns focus to the password for another attempt.

\code{nodwyn keychain init -{}-no-passphrase} (or ``Don't protect it with a
passphrase'' in Settings) makes a keychain that opens by itself, even in an
unattended run with no terminal. It is still encrypted, but under a key
anyone can derive: it is as safe as its file permissions and no safer, and
anyone who can read the file, or a backup of it, can use every key in it.
Not recommended; \nodwyn{} says ``no passphrase'' wherever it opens one.

The console's Connections \textrightarrow{} Credentials page lists the keys,
where each may go and what uses it, and adds, replaces, allows, authorizes
and removes them. From a session, a key is stored like this; the input is
masked, never logged, never echoed:

\begin{txt}
you> :eval (credential-register "weather-key")
\end{txt}

The front-end asks for the key in a masked prompt, stores it, and returns a
handle such as \code{\#<cred:weather-key:\ldots>}.

What comes back is a \textbf{handle}. It prints as
\code{\#<cred:class:id>} and nothing in the language can turn it into the
key: not \code{display}, not \code{format}, not \code{json-emit}, not
string concatenation. \code{credential-register} is user-only: neither the
model nor the loop's strategy can put a key prompt in front of you.
\code{(credential "weather-key")} looks up the handle of a key already
stored, or returns \code{\#f}; it is refused to the model, while the loop's
strategy may use it (the plan gate looks up the judge's key that way).

\section{Bindings: where a key may go}

A handle alone opens nothing. \file{bindings.toml} says where each class of
key may be sent, and how:

\begin{toml}
# ~/.config/nodwyn/bindings.toml
[[bind]]
class = "weather-key"
dest = "api.weather.example"
positions = ["query:appid"]
methods = ["GET"]

[[bind]]
class = "openai-key"
dest = "api.openai.com"
positions = ["header:Authorization:Bearer"]
methods = ["POST"]
\end{toml}

A position is where the key is injected:

\begin{itemize}
  \item \code{header:NAME}, optionally with a scheme:
    \code{header:Authorization:Bearer};
  \item \code{query:NAME}, a query parameter;
  \item \code{body}.
\end{itemize}

A service that uses OAuth2 (Google, Microsoft, GitHub, Notion, or an MCP
server behind a login) gets an \code{oauth2} credential, authorized in the
browser from the command line, never from a session:

\begin{sh}
nodwyn credential add --oauth2 google --client-id ID --scopes drive.file
nodwyn credential add --oauth2 custom --client-id ID \
    --auth-url https://auth.example/authorize --token-url https://auth.example/token
nodwyn credential list        # every credential, never a secret
\end{sh}

\code{google}, \code{microsoft}, \code{github}, \code{notion} and \code{openai} have
profiles; any other provider is \code{custom}. \code{-{}-client-secret}
asks for the client's secret when the provider needs one, and
\code{-{}-class} names the class (by default, the provider's name).
\code{add} prints the binding row to write, since nothing uses a credential
until a binding names it. The row may name the scopes it allows; a token
granted any other is refused:

\begin{toml}
[[bind]]
class = "google"
dest = "www.googleapis.com"
positions = ["header:Authorization:Bearer"]
methods = ["GET", "POST"]
scopes = ["https://www.googleapis.com/auth/drive.file"]
\end{toml}

The keychain refreshes the access token just before a use the table
allowed and the session logs \code{cred.refresh}. If the provider refuses
the refresh, every use is denied until \code{nodwyn credential login
CLASS}; \code{nodwyn credential revoke CLASS} revokes it at the provider and
deletes it here (\code{-{}-local} only deletes it here). Nothing opens a
browser in the middle of a turn: authorizing is something you do, at a
terminal.

With a \code{google} credential stored when a session starts, the session
offers the model \code{google-doc-upload}, which sends a document to
Google Drive as a new Google Doc (Chapter~\ref{ch:workspaces} has the
details). It needs only \code{POST} in that row, and only
\code{drive.file}. (\code{google\_credential} in the \code{[docs]} table of
\file{config.toml} names another class.)

The binding table is checked on every
request, before anything is sent; an unbound combination is never sent.
Only you edit it: the file is policy, and \code{policy-write} is user-only
and shows you a diff first.

\section{\texttt{http-request}}

\begin{scm}
(http-request cred url method position headers body)
;=> (("status" . 200) ("body" . "..."))
\end{scm}

The key is injected at \code{position} on the way out, if the binding table
allows exactly (class, host, method, position). Handles cannot come from
JSON, so the model can never call \code{http-request} directly. You reach
it through a tool you register:

\begin{scm}
;; Look the key up once, while init.scm runs with your origin. The tool
;; closes over the handle; the model's calls could not look it up.
(define weather-key (credential "weather-key"))

(register-tool "weather"
  (lambda (city)
    (if (not weather-key)
        (error "no weather-key was stored when this session started")
        (let ((r (http-request weather-key
                               (string-append "https://api.weather.example/v1/now?q=" city)
                               "GET" "query:appid" '() "")))
          (if (= (assoc-ref r "status") 200)
              (assoc-ref r "body")
              (format "weather service answered ~a" (assoc-ref r "status"))))))
  '((doc . "Current weather for a city, as JSON from the weather service.")
    (params . (("city" "string" "a city name, e.g. Lisbon")))
    (egress . #t)))
\end{scm}

\begin{careful}
A registered tool's body runs with the origin of whoever called it. When
the model calls \code{weather}, the body runs as the model, and
\code{(credential \ldots)} is refused to model-originated code. That is why
the handle is looked up at the top of the file, at load time, and captured
by the closure (Chapter~\ref{ch:forms}). Holding a handle grants nothing by
itself: every use is still checked against the binding table.
\end{careful}

What comes back is tagged \code{external:http}, and it passes the same
redaction as every tool result before the model reads it.

\subsection{What the guard checks on the way out}

\begin{itemize}
  \item \textbf{The binding} for the handle: class, host, method, position.
  \item \textbf{L1}: the headers and body are scanned for anything that
    looks like a credential. A recognized key there is refused unless its
    class is bound for that host and method (then the binding says it may
    go). Command lines are scanned the same way. The URL is the
    destination: its host is checked against the bindings, not scanned.
  \item \textbf{L2}: content that came from your files or command output may
    not go to a destination no binding names.
\end{itemize}

And no redirect is followed. A keyed request, a judge call or a model
request that the server answers with a redirect fails with an error that
names only the host it pointed to (``the server redirected to HOST; nodwyn
does not follow redirects for keyed requests''): the binding was checked
for the host the request went to, and following would carry the key, the
body or the whole conversation somewhere else.

By default a keyed request that no binding covers is denied outright. With
\code{policy.unbound = "confirm"} in \file{config.toml}, it asks instead,
and the answer offers \key{B}: save this exact binding and allow. The binding is then in the
file, where you can read it and remove it.

\section{Models are egress too}

A model with a \code{credential} is a keyed destination like any other, and
the same binding must allow its host. Every request is checked and logged
as \code{egress.check}. The key usually belongs to a server, a
\code{[servers.NAME]} table with the provider, the address and the
credential, which the models on it name with \code{server = "NAME"}: one
key and one binding for every model a provider offers. A server is known by
its name, not its address, so an API-key server and a ChatGPT plan server can
both sit at \code{https://api.openai.com/v1}. When the app sets up
a model for you, it saves the server and writes exactly that binding: the
server's host, \code{POST} (and \code{GET}, for the model list), a bearer
\code{Authorization} header; for Anthropic, the \code{x-api-key} header
instead (\code{config.KeyPosition} says which a provider reads), and a key bound
as a bearer token is not released to it.

\code{provider = "anthropic"} is a kind of its own, the Messages API
(\code{POST /messages}, \code{anthropic-version: 2023-06-01}) in
\file{internal/llm/anthropic.go}: the system messages are the top-level
\code{system}, a turn's tool results are \code{tool\_result} blocks of one
user message, \code{max\_tokens} is always sent, an effort is
\code{output\_config.effort} with adaptive thinking (Claude 4.6 and later; an
older model's 400 is explained by \code{llm.Hint} and the Test), and a reply's
thinking is not sent back, since its signature is not kept. A model takes
\code{cache\_control} (Claude caches only when asked) and refuses
\code{dialect}, \code{cache\_key}, \code{output\_field} and \code{seed}
(\adr{8}, amended 2026-10-05).

The server may also set \code{dialect = "cerebras"} alongside
\code{provider = "openai"}. Set it in the user's \file{config.toml}
before starting \nodwyn{}: Cerebras reads assistant thinking in history as
\code{reasoning} and rejects the default \code{reasoning\_content}.
Omitting the dialect or using \code{"compatible"} preserves the existing
encoding, and keeps a reply's \code{reasoning\_details} (OpenRouter's
reasoning as the model's provider gave it, often encrypted) when it carries
them: the log keeps the array as it came, and later requests send it back on
that reply, in place of its thinking text, to the same server and model only
(\adr{9}, amended 2026-10-15). \code{dialect = "responses"} sends each
request to OpenAI's
Responses API (\code{POST /responses}) instead: some of its reasoning models,
gpt-6.1-sol among them, take an effort beside tools only there. The effort goes
as \code{reasoning.effort}, \code{store} is false, and a reply's thinking is
not sent back, since that API takes reasoning back only encrypted; the
binding is the same host, \code{POST} and bearer header. The OpenAI preset in
Settings fills it in. A model with no server may set its own dialect; a model naming a
server inherits it. Unknown dialects and dialects on Ollama are refused.
Settings saves and model choices retain the dialect, including moving an
inline control into a server at the same endpoint, and Settings
$\to$ Models sets it with the rest of a provider; no URL inference is
involved. The log, window and credential binding keep their existing rules
(\adr{8}, \adr{9}).

\section{Efforts}

A reasoning model takes an \emph{effort}, how hard it is asked to think
before it answers, and a provider that does not know the field may refuse the
request. So \nodwyn{} never guesses which model takes one: a model's entry
declares the words its provider accepts, and a model that declares none is
offered none and sent none.

\begin{toml}
[models.deep]
server  = "openai"
model   = "gpt-5.1"
efforts = ["low", "medium", "high"]   # as the server spells them
effort  = "medium"                    # the start; unset leaves it to the provider

[models.local-thinker]
server  = "local"
model   = "qwen3:8b"
efforts = ["off", "on"]               # Ollama: think false / true
\end{toml}

The word reaches a chat-completions server as \code{reasoning\_effort} and
Ollama as \code{think} (\code{off} and \code{on} are its booleans; any other
word is a level, as gpt-oss takes). Words are short and lower-case.
\code{[control]} lists no \code{efforts} when an entry is the same model at
the same address: it takes them from that entry, so they are written once and
cannot go stale; its own \code{effort} is the default model's. A default that
is not among the efforts, or an effort on a model that declares none, is
refused when the file loads. Each \code{llm.req} records the effort it asked
for, so the request still replays to its hash (\adr{41}).

\section{Providers, models and the pickers}

Settings $\to$ Models is the file's \code{[servers]}, \code{[models]} and
\code{[control]} without the file. A \emph{provider} is a server: its kind, its
address, its dialect and its key. A key goes to the keychain with two binding
rows (the host, \code{POST} and \code{GET}, a bearer header; Anthropic's
\code{x-api-key}), is replaced in place, goes only
over HTTPS or to this computer by default; the user's
\code{policy.allow\_insecure\_http} setting also permits a remote HTTP provider.
It follows a change of path but never of host.
Each provider says whether it can be used and what to fix: the key's state is
read from the keychain and the binding table before the server is asked
(\code{needs\_key}, \code{locked}, \code{unbound}), then the server
(\code{unreachable}, \code{missing}). \textbf{Test} sends one short request
through the same binding check a task's request passes, and reports a key the
server did not accept, a model it does not have, or an effort it refuses.
\emph{Models you can choose} is \code{[control]} and the \code{[models.NAME]}
tables, with their efforts; the default is one of them, and choosing another
keeps the old default in the list. Each model has its own settings, edited in
its form: its context length and the reply cap that comes out of it (with a
line saying what the conversation is left with), its prices, whether it
takes images, and under More settings its sampling and what its requests ask
of the provider. They are its \code{[models.NAME]} entry's. \code{[control]} names
the default and its effort, and takes each setting it leaves unset from the
first entry for the same model at the same address (\code{Config.Tuned}), as
it takes its efforts; saving the default moves what \code{[control]} held to
the entry, so no copy goes stale beside it (\adr{41}, amended 2026-10-05).
OpenAI's and Cerebras' model lists say no context length and their replies no
cost (Anthropic's list gives the context, its replies no cost), so what their entries leave unset comes from \code{internal/catalogue}:
a snapshot of models.dev built into nodwyn, matched by the host of the server's
address (from a table in nodwyn's source, never from models.dev) and the
model's exact id, which gives the context, the longest reply (the reply cap,
at most a quarter of the context), the efforts, whether it reads images and
the prices, cache writes and a long prompt's tier included
(\code{Config.WithPublished}, \code{Config.Efforts}, \code{models.published});
OpenRouter's list and replies say both. A list is asked with the provider's key, through the
same binding check, since OpenAI, Cerebras and Anthropic list their models only to one;
a model key is bound for \code{GET} as well as \code{POST}.

The New task window and a conversation share one picker, a Model select
grouped by provider, an Effort select of what that model takes, and, where a
judge is set up, a Judge select (\adr{47}). New task
shows both fields; a conversation tucks them behind a compact model-and-effort
summary, opened by a click or by focusing it and pressing Enter. Warnings and
change notices remain visible when collapsed, and an unavailable conversation
opens the selects automatically so a model can be chosen. In a
conversation a change is a \code{session.model.set}; naming the model it is on
changes the effort alone, and nothing is sized again. Timing notices describe
actual choices; an unchanged running response shows no change notice.
While a response runs the
change is \emph{queued}: recorded at once without a window recipe, reported in
\code{session.info}, and applied as the turn ends, before it is idle. If it
cannot apply (the conversation outgrew the target's context, the model left the
list) the conversation keeps what it had, and the state and the log say why.
A conversation whose recorded model, or effort, \code{config.toml} no longer
offers opens as \code{unavailable} and asks no turn until a model is chosen: it
is never handed to another model, which would send its content to a provider
nobody chose for it. All of it is this computer's act, not a paired
device's. The terminal client offers the same list: \code{:model} shows it
with the conversation's model, and \code{:model NAME [EFFORT]} chooses.

A conversation may be moved to another model between turns
(\adr{40}). The choice names a \code{[models.NAME]} entry, config.toml's
\code{[control]} model, or a server and one of its models, so the key
never changes: another model on the same server is the same address and the
same key, and a switched model on another server brings that server's key
and its own binding, checked on the request as every other request is. The
choice, and the effort chosen with it, is a record in the session's log
(\code{session.model}) and is restored when the session is resumed; it is this
computer's act, not a paired device's, whether the task is being opened or
moved. The window is sized for the model that will answer, as opening the task
on it would size it (from \code{num\_ctx}, or the context the server's model
list gives), and a switch is refused when the conversation would not fit it.
Whether a model takes images is asked of each model the task is moved to: Ollama
says, and a chat-completions model is taken to unless its entry says
\code{vision = false} or, its entry saying nothing, its provider publishes
that it reads none, since a refused request costs less than an image
refused after a message was written around it (\adr{22}, amended).

An attached image is egress of a kind no binding governs: its pixels cannot
be redacted. It goes to the control model's host only, and only after a
confirm that names that host (Chapter~\ref{ch:workspaces} shows it); a
model you route to at another host gets a line saying the image is not for
it.

\section{What a request costs}

A hosted model is paid by the token, and a provider caches the start of a
prompt it has seen, at a lower price. For each reply, \nodwyn{} records
what the provider reports: the prompt and reply tokens, how many prompt
tokens came from its cache, and the cost in US dollars (OpenRouter reports
all of them).
For a provider that reports no cost (OpenAI, Cerebras), give the model its
prices, in dollars per million tokens, in its Settings form or its entry, and
\nodwyn{} estimates:

\begin{toml}
[models.coder]
server = "openai"               # a [servers.openai] with the url and key
model = "gpt-5.1-codex"
price_input = 1.25              # example prices: copy your provider's
price_cached_input = 0.125      # unset: as published, else price_input
price_output = 10
\end{toml}

A cache discount needs the provider to cache at all. Most hosted models cache
the start of a prompt by themselves, and the session key only routes a request
to the replica holding it; a Claude model through OpenRouter, Bedrock or
Vertex, or on Anthropic's own API, caches nothing until the request asks, and is billed for its whole prompt
on every request, reading \code{cached\_tokens: 0} with no cache write. Its
entry says so, \code{cache\_control = "ephemeral"} (five minutes) or
\code{"1h"}, and \nodwyn{} sends it as the request's top-level
\code{cache\_control} (\adr{9}). It is never inferred from a model's name; it
changes the wire and not the request's hash; and Settings'
\textbf{Test} sends it, so a route that refuses the field is found there.

An estimate needs an input and an output price, each the entry's or, left
unset, what the provider publishes, so a price typed alone is kept; it
prices cached prompt tokens at \code{price\_cached\_input} and reasoning as
output, and cannot know a provider's surcharge for writing its cache, so a
reported cost always wins. The same keys work in \code{[control]}.

Where you see it:

\begin{itemize}
  \item after each reply, the usage line in the terminal and the terminal
    client, \code{12,400$\to$800 tok · 78\% cached · \$0.012}, with
    $\approx$ before an estimate (Chapter~\ref{ch:first}); the console
    sums a turn's requests on one such line;
  \item at a budget checkpoint, what the turn has cost so far, ``at least''
    when some requests had no known cost; and, if you set
    \code{cost\_hard} in \code{[budget]}, a checkpoint and a stop on what
    the whole task has cost (Chapter~\ref{ch:first});
  \item the console's side panel, ``Totals'' in its Statistics tab, reads the
    daemon's derived log index, including for closed tasks. It shows turn and
    CLI driver and scheduled run counts, their latest start times in tooltips, and refreshes
    after recorded events. Changes reads approved previews and attachment
    metadata from the same index. A conversation with run records
    opens at the latest run, with Earlier runs paging five last-reply previews
    at a time and fetching their contents only on expansion. Older renderers
    do not change the live model or prompts; read failures can be retried.
    Inspectors label their latest-run scope; totals remain whole-task. The task
    header menu's Search finds messages and tool results in this task or other tasks
    of its project, grouped by task and turn. A match opens bounded, read-only
    history; Open task returns to current interaction (\adr{51}). A task
    without run records keeps its full conversation. Scheduled messages and
    manual Run now reset their per-run spend base; human follow-ups share it.
    The open task adds This run and applies spend warnings to it, while
    Totals remain whole-task (\adr{49}). Its figures include the whole
    task's spend, the judge's priced cost counted in, ``at least'' when a
    request had no known cost, how long the task's turns took all in, how
    long they took without the time it spent waiting for your answers, how
    much of that went waiting for a model's reply, and how long its tool
    calls ran with the wait for an approval left out; also ``Token cache
    rate'', the rounded whole-session percentage of raw prompt tokens read
    from cache, summed across turns and models before dividing. Only model
    replies reporting cache reads and prompt tokens count; missing or
    unreported usage stays out. A reported zero with positive prompt tokens
    gives 0\%; without a positive prompt total it says ``unknown''. This
    measures prompt-token share, not the percentage of requests hitting
    cache or the budget's discounted token count. If history was truncated,
    the Totals label ``from the log that remains'' applies to the rate too
    (\adr{9}). A compact summary above every tab keeps three figures available:
    total spend, turn time and context fullness; the tool calls and the
    cache rate are in Statistics. Progress
    holds the plan, Workspace includes retained project notes, and the four
    tabs, above the content, stay on one
    row at both desktop panel widths, retaining visible keyboard focus.
    Navigation stays outside the desktop content's scroll area. A worktree
    task's Review button opens its actual branch diff in the centre; Home's
    Recently finished Review link does too. Unified is the default, with a
    Side-by-side option; Close review restores conversation/reply while
    retaining review drafts and reading position. Comments use current-file
    numbers in either layout, with whole-file comments for old-only deletions.
    Changes' approval previews and recovery stay separate; narrow screens
    stack normally, with split diffs scrolling inside their body rather than
    widening the page;
  \item \code{:budget} in the terminal client: the latest turn's spend over
    all its model requests and the share of prompt tokens from cache, or
    why the spend is unknown;
  \item in the log, \code{llm.resp}'s \code{usage} (Chapter~\ref{ch:log}),
    and in Scheme, \code{model-turn}'s \code{cached-tokens} and
    \code{cost} (Chapter~\ref{ch:turn}).
\end{itemize}

Unknown is never shown as free. A cost stops a task only at a spend limit
you set, and a cached prompt token counts a tenth of one against the token
budget. A low cached share on a long task is worth a look: it means the
start of the prompt keeps changing (trims, folds, compaction; see the tip
in Chapter~\ref{ch:contexts}).

\section{The judge}

The judge is a keyed service like a model, and a provider's like one
(ADR~46). The plan gate asks it whether a request needs a plan and how
good a plan is (Chapter~\ref{ch:plans}). A chat asks it first whether to
allow a command no standing approval covers (\code{[approval] commands =
"judge"}, the default; Chapter~\ref{ch:primitives}), and you when it does
not; a run started with \code{-{}-judge} asks it about every ordinary
confirm. Without a judge, those commands are yours to answer.

Its provider is one of two. Jev, TypeSafe's judge, is a provider of its
own kind, \code{jev}: it answers the judge's questions and has no chat
models, so no model can be put on it. OpenAI answers them through its
Decisions API with \code{gpt-6-luna}, with the key an OpenAI server at
\code{https://api.openai.com/v1} already has for its models. A ChatGPT
plan's sign-in cannot ask it, since the keychain sends a plan's token only
to its chat endpoints, so such a server is refused as a judge (\adr{47}).
In the console, Settings \(\rightarrow\) Judge sets either up in place:
paste Jev's key, or an OpenAI API key, and that is all, since each judge's
model and price are known; its key goes to the keychain, allowed for its
host by POST alone, and a judge added when there is none becomes the
default. A task asks \code{[judge]}'s judge unless it chose another, beside
its model, in the New task window, its conversation, or the terminal's
\code{:judge}; each choice is a \code{session.judge} record, and a resumed
task asks the judge it chose. By hand, a server and the \code{[judge]}
table that names it:

\begin{toml}
[servers.jev]
provider = "jev"
url = "https://api.typesafe.ai"
credential = "jev-key"

[judge]
server = "jev"                    # or an OpenAI server with an API key
content = "plan"                  # none, plan (the default), plan+summaries or full
approve_threshold = 0.8           # a call it judges runs at this probability of allow or above
price_input = 0.5                 # US dollars per million tokens, to price
price_output = 2.0                #   what the judge reports it used; unset,
                                  #   its questions are priced as published
\end{toml}

\begin{txt}
you> :eval (credential-register "jev-key")
\end{txt}

\begin{toml}
[[bind]]
class = "jev-key"
dest = "api.typesafe.ai"
positions = ["header:Authorization:Bearer"]
methods = ["POST"]
\end{toml}

The judge asks its provider's model (\code{jev-latest}, \code{gpt-6-luna}),
which is all either API answers to; \code{model} and the prices above apply
only on the server \code{[judge]} names, and Settings says when
\code{model} names one its provider does not answer to, with a button that
clears it. A \file{config.toml} that still has the
old \code{[jev]} table does not load, and says what replaces it. The
thresholds were set against Jev's probabilities; another judge may put the
same command higher or lower.

\code{content} is how much may leave for the judge. At \code{none} there is
no judge. At \code{plan} the plan gate sends the request and the plan, and
a judged call is described by its tool, reasons and target. At \code{full}
the judge also sees what a judged call would write or send, and a session
offers the model the judge's three primitives as tools of its own:
\code{judge-yes-no} (a yes-or-no question; the probability of yes),
\code{judge-score} (a rating along levels the model lists) and
\code{judge-choice} (one of several options). Below \code{full} they are
hidden, for the plan gate and your Scheme. They exist only in a session
that started with the judge's key stored; Go looks the key up when the
call is made, and the guard checks the call against the binding of the
judge's server, whoever made it. Every string sent is redacted first, whichever API it goes to, and
\code{jev.req} logs each call, never its text.

The judge reports what each request used, in tokens, and never what it
cost. \nodwyn{} records the counts and the model that answered with each
call, and prices them with \code{price\_input} and \code{price\_output},
each one you leave unset the published one: Jev's \$0.042 and the
Decisions API's \$0.10 per million input tokens, both with nothing for
output. Each call is a line in the conversation
(\code{[judge choice: 318$\to$34 tok · $\approx$\$0.0002]}), and the running total
is in the console's side panel, at checkpoints and in \code{:budget}. Its
tokens are not model tokens and stay out of the token budget; its cost
counts against a spend limit.

\section{MCP servers}

MCP servers offer tools. \nodwyn{} treats a server as a destination it
does not trust. In the console, \textbf{Connections \(\rightarrow\)
Tools} adds one, remote (HTTPS only; a key goes to the keychain, bound to
that host only) or contained on this computer (below), lists its tools for
review, and records in \file{mcp.toml} what you decided, including the
workspaces it is offered in. \nodwyn{} never runs a local server as a
program of its own: only in a container.

\begin{itemize}
  \item \textbf{A pinned manifest.} You approve the exact tool list: every
    name, description and schema is hashed. If the server later changes
    any of it, new tasks withhold its tools and say why, until you review
    again.
  \item \textbf{Declared effects.} For each tool you say whether it
    \emph{reads} or \emph{changes things}. A tool with no declaration is
    treated as both: it asks every call and offers no standing answer.
  \item \textbf{Nothing on by default.} A new server offers nothing, and a
    new tool is off until you turn it on, and then only to new tasks in the
    workspaces you chose.
\end{itemize}

The model sees an MCP tool as \code{server\_\_tool} (model APIs refuse
slashes in tool names); the console shows \code{server/tool}. Arguments are
egress to the server's host, and every one is a payload: L1 refuses a
recognized key in any of them, however deeply nested, unless its class is
bound for that host, and L2 lets content from your files or command output
go there because you approved the server, with a key or without. Results
are ingress: redacted, tagged \code{external:mcp}, and never instructions.

\begin{tip}
The confirm for an MCP call is not really ``is this argument safe?''. It
is ``do I want this third party to see this?''. The prompt names the
server, the host and what is being sent, so you can answer that question.
\end{tip}

\subsection*{A server on this computer}

A local server never runs as a process of yours. \nodwyn{} runs it in a
container, with podman or docker (\code{[mcp] runtime} in
\file{config.toml}), from an image pinned by digest; a tag is refused. You
choose what it can reach:

\begin{itemize}
  \item \textbf{Network.} \code{network = []}: none at all. A list of hosts:
    its only way out is \nodwyn{}'s egress proxy, which lets through
    exactly those hosts (ports 443 and 80, or \code{host:port}) and records
    every attempt as \code{mcp.egress}; the task shows the refused ones.
  \item \textbf{Files.} \code{mounts}: workspace folders it sees under
    \code{/workspace}, read-only unless \code{:write}. Never the workspace
    itself, never \code{.nodwyn/}.
  \item \textbf{A key.} \code{position = "env:NAME"}: the variable it
    reads its key from. The key goes in at start only if its class is bound
    for every listed host at that position; with no network it is refused.
\end{itemize}

A task never downloads code: \code{nodwyn mcp pull NAME}, or Pull in
Connections, fetches the image by its digest. Everything else is fixed: no
capability, a read-only root, none of your environment, and the container
is removed when the task ends. A confirm names ``the contained server NAME
(network: \ldots)''. An HTTP client in the server that ignores
\code{HTTPS\_PROXY} reaches nothing.


\section{ChatGPT plan credentials for OpenAI models}

In Settings, Models, add an OpenAI provider and choose ChatGPT plan.
Unlock the keychain and Continue with ChatGPT; finish consent in the browser.
Choose the connected account and Save the provider: its credential class,
fixed public API address, Responses dialect and model bindings are saved
without editing files. Add a model from its list, Test it, and choose it as
the default. Existing accounts can be selected, and Sign in again renews
consent. Switching to API key requires a new key and preserves the account.
The terminal route below prints the configuration to install by hand.


\begin{sh}
nodwyn credential add --oauth2 openai
nodwyn credential login openai
nodwyn credential revoke openai
\end{sh}

OpenAI dynamically registers a public client during the first consent;
no client id or secret is needed. Connections offers the same profile and
Continue with ChatGPT action. Give each account a distinct \code{-{}-class}
when adding it. Add the printed bearer binding for \code{api.openai.com}
and configure its model provider:

\begin{toml}
[servers.chatgpt]
provider = "openai"
url = "https://api.openai.com/v1"
dialect = "responses"
credential = "openai"
\end{toml}

Select an account-visible model on that server in \code{[control]} or
\code{[models.NAME]}. Restart the daemon after editing its configuration.
OpenAI controls model access, plan eligibility and quota; Try in Models
checks the selected model. No refusal falls back to API-key billing.

The flow pins the OpenAI issuer, validates an asymmetric JWKS signature,
issued-client audience, expiry and fresh nonce, and requires plan-use
scopes. Reauthorization reuses the saved client and stable host, validates
the same account subject, and retains the old credential on failure. It
omits optional ID-token hints from authorization URLs. Tokens stay in the
keychain; a serialized refresh rotates both tokens together, and revocation
uses the same issuer's discovery endpoint. The stable host is persisted
before consent, even when cancelled, in keychain version~3, so older
binaries refuse to rewrite it.

A plan credential may be injected only as a bearer header into public
\code{GET /v1/models} or \code{POST /v1/responses}, even with a broader
binding. The account model list keeps visible slugs. Responses requests
set \code{store = false} and \code{stream = true}; output is buffered through
a terminal response before redaction, preserving ADR~25 for secrets split
across deltas. A disconnected stream without a terminal event is an error.
Manage app permissions and quota in ChatGPT Settings.

\section{Transport and storage choices}

Keyed requests require HTTPS except on localhost and literal loopback addresses.
A user may explicitly allow remote HTTP through Settings > Keys \& devices > Credentials
over remote HTTP, or \code{[policy] allow\_insecure\_http = true} in config.toml.
It defaults to false. New/resumed tasks use the saved value; provider setup, tests
and model lists use the current user setting. HTTP exposes the key and payload to
anyone on the route. Binding checks, redirect refusals, certificate verification
and the special ChatGPT credential sinks still apply. Separate MCP, OAuth endpoint
and Google upload URL validation is unchanged.

The keychain format and default KDF are unchanged. Readers bound file size to
16 MiB and validate Argon2 parameters before key derivation. Writers use random
exclusive 0600 sibling files, sync, rename and sync the directory. A directory-sync
failure after rename is reported with uncertain durability; the published key
remains in memory. \file{docs/security.md} gives the exact parameter bounds and
migration limits (ADR 45).

\paragraph{Scheduler ownership and context (\adr{49}).}
The daemon holds a data-directory flock and checks civil-time occurrences
on startup and every 30 seconds. A definition's rule (once; set times or an
interval within a daily window; weekdays, dates or the nth weekday of a month;
a first minute and a last day) is stepped through day by day in civil time;
the five repeats from before rules are read as the rules they meant, so old
logs run at the same times. The daemon writes the rule's sentence into each
session.schedule record and answers schedule.read with the sentence, labelled
next times, its named zone and the latest twenty times, each with its outcome
and cost, folded into the log index beside the schedule, with the day's runs
and cost (\texttt{today}) that a daily spend limit is checked against; once
reached, one schedule.skip stands for the rest of the day's automatic times. The log is the authority: session.schedule
holds the latest definition, schedule.run claims a due interval and pins its
spend base, and schedule.skip consumes a skipped interval. Manual runs consume
no automatic time. Pausing preserves progress; resuming sets it to now.
Archive pauses the definition. A log another process owns cannot be written:
its skip is deferred in daemon memory until release; if the daemon stops
first, restart handles that interval as missed. A task closes after 15 idle
minutes with no pending answer. Nothing schedules through Scheme, and only
this computer creates or changes a definition; paired devices may pause or
run now. A login item (\texttt{internal/startup}: a systemd user unit and
its default.target.wants link, or a launchd agent) runs the daemon at login,
written only on request (startup.set, nodwyn startup), never over a file
nodwyn did not write, and never for a go run build; the daemon then clears
a socket a crash left before listening. With notify.desktop on, a daemon
given a notifier (WithNotify) shows fixed notices when a session's
needs\_answer turns on with no local client in session.watch, and once per
locked period when a locked keychain skips a scheduled run.

\paragraph{Workflows that watch a source (\adr{53}).}
\texttt{internal/watch} reads a forge's open pull requests with the key the
binding table allows at that host for GET (the table's own lookup, as the
guard makes it for http-request; no redirect is followed and the body is
bounded) or the JSON lines of a command run with no shell; it fires what is
new against what was seen, by id and version, after the filters.
\texttt{internal/workflow} keeps each workflow's log in the data directory,
written by the daemon that holds scheduler.lock, redacted as a task's records
are. A run attaches the event as a file, so the window frames it as data, and
sends the instruction as an ordinary scheduled turn: the event is never a
user message, and no primitive makes or changes a workflow. A run whose
answer is to be posted is tracked in memory until its task goes idle; the
host then reads the final reply from the log into a workflow.outbox record,
and only on a decision, or the workflow's own choice made on this computer,
posts it with the binding table's lookup for POST, so a run that read a
hostile pull request has nothing to send with. Every poll and post goes
through core.Keyed.Authorize, the check a task's model requests meet: the
binding table read afresh, the credential's granted scopes against the row, the
transport rule and an OAuth2 refresh. A Gmail source keys a thread by its id
with its newest message's id as the version, reads a message in full only for
a change, and writes a draft reply whose headers are built from the sender's
address, parsed, and values with their line breaks removed.

A successful turn that added more than a quarter-window since its last note
asks compact-note for a handover focused on the scheduled request. It keeps
the turn's budget, skips tool calls and records context.handover without
narrowing the current chat. The next scheduled message applies a lasting
narrowing and the note, then sends the request. Human replies retain the
conversation. Pending answers suppress preparation.
