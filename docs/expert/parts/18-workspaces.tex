\chapter{Workspaces, attachments and undo}
\label{ch:workspaces}

\nodwyn{} started as a coding agent, and git was its undo. It now works in
any folder: a code repository, a folder of documents, a mix. This chapter
covers what changes when the folder is not only code, and how to get
things back.

\section{A workspace}

A \textbf{workspace} is a folder you named, with the other folders its
tasks may use: its \emph{mounts}. Both are kept in \file{workspaces.toml}
in the config directory, never in the folder. A folder nobody named is a
plain workspace: that folder, writable, nothing else.

\begin{toml}
# ~/.config/nodwyn/workspaces.toml
[[workspace]]
name = "Garden"
path = "/home/me/garden"

[[workspace.mount]]
path = "/home/me/Reference/garden-books"
access = "read"

[[workspace.mount]]
path = "/Volumes/Shared/seed-orders"
access = "write"
\end{toml}

A mount is another folder a task may use, by absolute path (or
\code{\textasciitilde/}), \code{read} or \code{write}. A read-only mount
refuses every write. Mounts may not overlap the workspace or each other, and
\code{/} or your whole home folder is refused as too broad. A task in a
git worktree of its own has its repository's mounts.

The console's \textbf{Workspaces} page edits this for you, and Home offers
the folders it names. \textbf{Forget} is available for named folders and
folders known only from tasks: after confirmation it removes the name and
mounts and keeps the folder out of Workspaces and Home's suggestions, even
after a restart. The folder, files and task history are untouched; open
tasks keep their mounts. A matching last pick is cleared. Using the folder
again clears its forgotten marker: adding it, or a task started or resumed
there, since session start in core clears a marker that names its folder.
Forgetting is local to the computer running \nodwyn{}, not offered to paired
devices, which may still choose a forgotten folder by its path. From Scheme:

\begin{txt}
you> :eval (workspace)
(("mounts" (("path" . "/home/me/Reference/garden-books") ("access" . "read")) ...))
\end{txt}

When a workspace has mounts, the default system prompt adds a section
naming them, so the model knows to reach them by absolute path.

\begin{careful}
The mounts live in the config directory, which the guard keeps from the
model: it cannot widen its own mounts, and a repository cannot either, since
nothing in a folder is read for them (\adr{22}). A
\file{.nodwyn/workspace.toml} from an older \nodwyn{} is ignored; add its
mounts again on Workspaces. Changing them is your decision, in the console
or by editing the file, and applies to tasks started afterwards.
\end{careful}

\section{Undo where git is not the undo}

Writes in the folder go ahead without asking (Chapter~\ref{ch:primitives}),
so each one must be possible to take back. Before \code{fs-write},
\code{fs-edit} or \code{doc-export} replaces a file, \nodwyn{} keeps its
previous content in \file{.nodwyn/versions/} and records a
\code{file.version} event, unless git can give it back:

\begin{txt}
you> :eval (fs-edit "plants.txt" "basil" "basil\nmint")
· ⚑ writes in the folder go ahead (approval.writes)
· --- plants.txt
· +++ plants.txt
· @@ -1,2 +1,3 @@
·  tomatoes
·  basil
· +mint
[kept the previous version of /home/you/garden/plants.txt]
\end{txt}

In a git work tree, each write asks git (\code{git status}) whether the
file is committed and unchanged; only then is git the undo, and nothing is
kept. A file with uncommitted changes, an untracked file and an ignored one
keep a version, so the store appears in git repositories too. Its own
\file{.gitignore} keeps it out of \code{git status}.

\begin{sh}
$ nodwyn versions plants.txt
2026-09-30 13:19:00  55d684f93ad3      15 bytes
$ nodwyn undo plants.txt
Restored /home/you/garden/plants.txt to its version of 2026-09-30 13:19 (55d684f93ad3).
\end{sh}

In the console, a task's \textbf{Changes} list has \textbf{History} per
file. \textbf{Compare with current file} reads a kept version and today's
file without writing: removed lines belong to the kept version, added lines
to the current file. A missing current file appears as deletions. Empty and
oversized comparisons say so; compare again to refresh. This is not the
recorded approval preview, which may be unavailable on older records and
never proves execution succeeded. \textbf{Restore} writes a kept version back as a write like any
other, so it goes ahead without asking, its diff logged (it asks when
\code{[approval] writes = "ask"}), and keeps the current content as a
version too, so a restore can itself be undone. The store is capped per
folder.

\begin{tip}
In a git repository, git is the undo for what it has committed:
\code{git diff} and \code{git checkout} are your tools, and the version
store keeps only what git could not give back. The model gets two of its
own there, \code{git-status} and \code{git-diff}: read-only, so they need
no approval, and run with everything in git that could start another
program switched off (external diff drivers, text conversion, the pager),
with credential-looking files left out. Commit before a big task, and
review with \code{git diff} afterwards; with writes in the folder going
ahead, that is the fastest safe way to let \nodwyn{} make a large change.
\end{tip}

\section{Attachments}

In the console, the paperclip attaches files to your next message; in the
terminal client, \code{:attach PATH} does, with \code{\textasciitilde/} for
your home and a relative path read from where \nodwyn{} started. Both take
text formats, Word (\file{.docx}), Excel (\file{.xlsx}), PowerPoint
(\file{.pptx}), and PDF when \code{pdftotext} is installed, and images
(below). Each file other than an image is:

\begin{enumerate}
  \item copied into the folder's \file{.nodwyn/attachments/};
  \item turned into text, redacted (secret-looking strings hidden) and
    capped;
  \item recorded as an \code{attach} event and shown to the model
    \emph{as data}, not as instructions.
\end{enumerate}

The conversation shows a chip per file with how many secret-like strings
were hidden. The model reads the extracted text; the copy in
\file{.nodwyn/attachments/} is ignored by git, so it never ends up in your
repository's diff.

\begin{careful}
``As data, not instructions'' is a framing the model is given, not a
guarantee it obeys. A document can still say ``ignore your task and
\ldots''. What the guard guarantees holds regardless: whatever the model
decides after reading it still has to pass through the door.
\end{careful}

\subsection{Images}

A PNG, JPEG, GIF or WebP (decided by what the file contains, not its name;
at most 10\,MB and 8000 pixels a side) is sent to the model as an image, so
it can only be attached when the conversation's model takes images: Ollama
says so itself, and a chat-completions model does if its table says
\code{vision = true}, or nothing and its provider publishes that it does or
publishes nothing of it (Settings $\to$ Models, Takes images); a model that
cannot read one refuses that request, and the turn says so.
Nothing redacts pixels, so the task asks first, every time:

\begin{txt}
─── confirm: attach image whiteboard.png
  • whiteboard.png is an image (PNG, 1200×800, 32 KB, about 1,105 tokens).
    Its contents cannot be redacted: whatever it shows, a password or a key
    included, reaches the model as it is, and nothing in it is read as text.
  • It goes to the control model qwen2.5vl at workshop:11434, another machine:
    its pixels leave this computer as they are.
  • It goes with later requests to that host only, while the conversation
    shows it; the judge never gets it.
allow? [y/N]
\end{txt}

It is a security confirm: \key{Y} covers this image only, \code{--yolo}
never says yes to it, and \code{--no-confirm} says no. The chip then reads
``image · 1200×800 · \textasciitilde1,105 tokens'', which is what the
picture costs the context. The log keeps its size, digest and the host you
allowed, never the pixels. A request to any other host gets a line saying
the image is not for it, and the planner and sub-agents, which start in a
context of their own, never see it.

\begin{tip}
To take an image back out of a conversation, delete its copy under
\file{.nodwyn/attachments/}. Later requests then say it is missing; they
never send a different picture in its place.
\end{tip}

\section{Documents out}

The model can also write documents. \code{doc-export} turns Markdown or
LaTeX into Word, OpenDocument or HTML with pandoc (2.15 or later; without
it the tool says what to install):

\begin{scm}
(doc-export "report.md" "out/report.docx")
;=> "wrote out/report.docx (Word document, 10 KiB) from report.md"
\end{scm}

It is a write: it goes ahead like any write in the folder (with
\code{[approval] writes = "ask"} it asks, with source, target and
formats), and replacing a file keeps the old one in the version store.
pandoc reads the document in its sandbox, so an
include or a remote image in it reads nothing, and a Word or OpenDocument
file embeds only images that are files in the folder. An HTML page leaves
out an image that links elsewhere, which a browser would fetch when the
page is opened. Raw content written into the source (an HTML block, a Word
field) comes out as text, never interpreted. The answer says which images
were left out and when raw content was shown as text.
There is no PDF: a TeX engine reads any file and runs programs when a
document asks, so build a PDF with \code{shell-exec} and \code{latexmk}, as
\nodwyn's own book is built.

With a \code{google} credential stored and bound (Chapter~\ref{ch:keys}),
\code{google-doc-upload} sends a \file{.docx}, \file{.odt}, \file{.html} or
\file{.txt} to Google Drive as a new Google Doc and returns its link:

\begin{scm}
(google-doc-upload "out/report.docx" "Q3 report")
;=> (("id" . "1AbC...") ("url" . "https://docs.google.com/document/d/1AbC.../edit") ("title" . "Q3 report"))
\end{scm}

The first upload asks how uploads should be handled from now on: \emph{allow
by hand} (every call asks you, naming the file, its size and where it
goes; \code{[approval]} never answers it, and \code{-{}-yolo},
\code{-{}-judge} and unattended runs never upload),
\emph{always allow} (no call asks; only this computer can choose it, never
a paired phone), or \emph{deny} (refused, and later sessions do not offer
the tool). The answer is \code{google\_upload} in the \code{[docs]} table
of \file{config.toml}; Settings in the console changes it, and the log
records it as \code{setting.change}.

\begin{careful}
The file's bytes never become a Scheme value, so the door cannot read them.
The upload reads them itself, every part of a Word file included, and
refuses one that holds something shaped like a key whose class is not bound
for Google; \code{doc.upload} in the log says what left, never what it
said. A contract or a salary list has no shape: what keeps it home is your
``no''.
\end{careful}

\section{Several tasks on one repository}

Tasks in one folder share its files, its git index and its stash, so one
task's edit shows up in another's test run. On Home, the checked-by-default
\textbf{In a worktree} beside a git workspace starts a task in a git worktree
of its own (\adr{34}): \file{.nodwyn/worktrees/<id>/} on a new branch
\code{nodwyn/<id>}, from the repository's \code{HEAD}. The worktree is the
task's root, with its own \file{.nodwyn/} settings; the notes, mounted
folders, MCP servers and history are the repository's, and the task is
listed under it. Uncheck the toggle to start in the folder itself; its
choice is kept per folder in this tab. In the terminal client the chooser's
first row in a repository's top folder starts a session in a worktree, and
\code{nodwyn tui -{}-worktree} starts one directly; its title shows the
branch.
Uncommitted changes are not carried over, and the conversation says how
many there were. \code{(worktree)} tells a strategy where the task works,
and the system prompt tells the model, with a warning against
\code{git stash}, which every worktree shares.

The console's \textbf{Review} button and Home's \textbf{Recently finished}
worktree \textbf{Review} link open the task's changes in the centre panel,
replacing the conversation until \textbf{Close review} restores it and its
reply draft. The changes are since the base commit (\code{worktree.diff},
read without the daemon's lock, capped in size and time). \textbf{Unified}
is the default, with old and current-file line numbers; \textbf{Side-by-side}
aligns replacements with blanks for unmatched lines. Long lines wrap within
the columns, and a phone scrolls the split diff rather than the page.

\textbf{Send review} sends comments as one message (\code{worktree.review}),
ordered by file and current-file line and carrying no file content. Old-only
deletions and explanatory notes have no line-comment control, but whole-file
comments are available. Send waits while the task works; only acceptance
clears comments and the overall note. Mode changes, redraws and closing/reopening
retain saved comments, the unfinished comment, note, reading position and
textarea selection in tab memory; reloading loses them. Failed refreshes keep
the preceding diff, and late replies cannot reopen a closed review. A closed
task's review says to resume it. Approval previews and kept-version comparisons
remain in Changes. Only comments are built, not branch approval/rejection;
a change of direction is a message of its own.

The work stays on the branch until you merge it. Closing the task removes
the worktree and its branch only when nothing would be lost: no change, no
untracked or ignored file, no commit its base lacks. Resuming a task whose
worktree was removed makes it again. The versions \nodwyn{} keeps of a
worktree task's files are the repository's, in its
\file{.nodwyn/versions/}: they never keep a worktree, and outlast it.

\section{Path aliases and older notes}

A project has one canonical path with existing symlinks resolved. The same folder
through macOS's \file{/tmp} and \file{/private/tmp} shares mounts, MCP selection,
notes and task grouping. Existing session logs and kept-version indexes remain
readable. Notes found through the requested spelling or old session records migrate
to the canonical key with \file{notes.md.before-path-migration} backups. Conflicting
notes or duplicate registered aliases require reconciliation rather than combining
permissions or discarding data. A managed worktree keeps its own checkout identity
and the main project's identity for shared resources (ADR 45).
